## Design — horizontal scaling architecture

### 1. Shard strategy: consistent hashing on persona_id

```
shard_id = sha256(persona_id).hexdigest()[:8] % N_shards
```

- **Linear scaling** in N_shards: adding a shard rebalances ~1/N_shards of personas with consistent-hash minimal-reshuffle.
- **No cross-persona joins**: retrieval, extraction, consolidation, and diff-engine rollback all operate within a single persona (T-016 + T-020 + T-032 all scoped per-persona).
- **No shared locks**: T-032 single-transaction consolidation is per-persona-scoped; no global lock.

### 2. Per-persona independence (load-bearing invariants)

Per theories/hypotheses:
- **T-016** (no cross-persona FK): Each persona is a self-contained memory store.
- **T-020** (SQLite-per-persona-file): Strongest possible per-persona isolation (each persona is its own DB file).
- **T-032** (single-transaction consolidation): Atomicity within a persona; no cross-persona coordination.
- **T-019** (Postgres JSONB row per persona row): In a shared-Postgres variant, all rows for persona_id=X live on a single shard; no cross-shard joins.

The diff-engine (§3.3) operates on `fact_diffs WHERE persona_id = X`; rollback is per-persona. Confirmed no cross-persona coordination.

### 3. Hot-persona skew analysis

Worst-case hot persona (celebrity, viral chatbot):
- Median persona: ~100 msg/mo, ~0.04 msg/min average.
- Hot persona: ~10,000 msg/mo, ~4 msg/min average. Ratio: **250×**.
- Extreme outlier (e.g., "influencer" persona): 100,000 msg/mo = ~40 msg/min. Ratio: **1,000×**.
- Human-upload-bounded: even the most active single persona cannot sustain >100-1000 msg/min (it's a single user's typing speed).

**Skew is bounded to ~100-1000× median**, well within shard-capacity tolerance (a dedicated shard can absorb up to 10,000× median by running alone).

### 4. Backpressure design

```
per-persona fairness token bucket:
  refill_rate = 10,000 tokens/min per persona
  burst_cap = 60,000 tokens
  admission: token_bucket.take(5040) or 429-with-Retry-After

global tenant pool:
  refill_rate = OpenAI Tier-N TPM quota (e.g., 2M TPM Tier 4)
  burst_cap = 2× refill
  second-level admission control
```

Noisy-neighbor isolation: A single hot persona cannot consume >10K tok/min, preventing starvation of the other personas sharing the tenant LLM quota.

### 5. Worked example — noisy-neighbor burst

Setup: 100 personas co-located on one shard; one persona bursts 100 consolidation cycles back-to-back.
- Without per-persona bucket: that persona consumes 100 × 30K = 3M tokens in burst → saturates 2M TPM quota → all 99 other personas get 429 errors.
- With per-persona bucket (10K tok/min): burst throttled to 10K tok/min; consolidation spread over 5 hours; other personas unaffected. ✓

### 6. Diff-engine per-persona scoping

§3.3 describes reversible consolidation — each consolidation event is a `fact_diff` record attached to a `persona_id`. Rollback syntax:
```sql
DELETE FROM facts WHERE persona_id = ? AND created_by_diff_id = ?
INSERT INTO facts ... FROM fact_diffs_prev_state WHERE persona_id = ? AND diff_id = ?
```
All scoped to single persona; no cross-persona coordination. ✓
