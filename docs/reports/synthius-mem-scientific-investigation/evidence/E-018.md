## Constructive Argument: 21.79ms Field-Level Matching Incompatibility with Composite Strings

CategoryRAG reports 21.79 ms mean latency on LoCoMo-scale data (500 MB, per §4). Field-level matching at this latency requires indexed lookup:
- Hash index: O(1) on exact field match — needs typed atomic fields
- B-tree index: O(log N) on range — needs typed atomic fields
- GIN/trigram index: O(log N) + scan — works on full-text columns but degrades with corpus size

If the storage form were `"PhD Neuroscience, UCL, 2019"` (one string), then:
- A query like "where did X get their PhD?" requires matching `institution = "UCL"` INSIDE the composite string
- This is substring search = O(N × L) where L = average string length
- 500 MB of biography data with, say, 200 K fact-strings × 40 chars avg = 8 × 10⁶ comparisons per query
- On modern hardware, 21.79 ms budget allows ~5 × 10⁷ operations at most — tight but feasible only with no parallelism overhead
- With multiple domains queried in parallel (paper describes planner LLM routing to multiple domains) and multiple facts per domain, substring scan is NOT the right primitive for 21.79 ms median

Typed atomic-field lookup is the natural primitive for 21.79 ms on this scale. Decomposed storage is the architecturally consistent choice.
