### 4. Worked example — major-version removal (retype)

Suppose a major version deprecates the string `category` field in favor of typed `category_id` (int foreign-key-style reference into an external enum table):

```python
# v1.1 → v2.0 (major: rename/retype a field)
CATEGORY_STRING_TO_ID = {"education":1, "employment":2, ...}

@migration("biography", "v1.1", "v2.0")
def bio_v11_to_v20(fact):
    old_category = fact.pop("category", None)
    if old_category is not None:
        fact["category_id"] = CATEGORY_STRING_TO_ID[old_category]
    return fact
```

The migration is idempotent (replaying it on an already-migrated fact is a no-op because `category` has been popped). The storage layer never touches the fact on read; only the in-memory hydration transforms it. ✓

### 5. Migration correctness properties

- **Idempotent on repeated reads:** Every migration only bumps `schema_version` as its final step; re-reading a freshly-written v1.1 fact when `current_v=v1.1` is a no-op (loop doesn't enter). ✓
- **Chaining works:** Reading a v1.0 fact when `current_v=v2.0` chains v1.0→v1.1→v2.0. ✓
- **Write path is always current version:** `write_fact` always stamps `schema_version=current_v`; old versions only exist on historical rows. ✓

## Reasoning

- `schema_version` already committed via T-003; this experiment operationalizes the migration machinery.
- Registry pattern `(domain, from, to) → fn` is the canonical shape for versioned data transforms (Django migrations, Rails migrations, Alembic all follow this).
- Minor bumps (enum widening, optional field addition) are no-op migrations — existing data remains valid.
- Major bumps (rename, retype, remove) require explicit migration functions; idempotent by construction (pop→reassign pattern).
- Re-extraction is deferred indefinitely: schema changes are absorbed by migration functions, NOT by re-running LLM extraction on the source corpus.
- Composable with T-019/T-020 storage substrates (both tolerate optional fields and version-stamped rows).
