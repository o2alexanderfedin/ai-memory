## Notable findings

1. **"Tools" language is plural but mechanism is undeclared.** The paper says "retrieval tools" (line 42, 46, 51) consistently in the plural, supporting T-025's 6-tool catalog. But whether these are OpenAI function-call tools (consumed by the planner LLM via tool-use API) or Python functions (called by the host orchestrator after planner output) is left ambiguous. This is a SEPARATE architectural hypothesis from H-060 (structured-output mechanism for EXTRACTION).

2. **"strict" occurs once in §7** as "strict evaluation conditions" — a false-positive for the structured-output term search. The paper does NOT use "strict" in the OpenAI-API sense.

3. **"No learned parameters"** (line 55, §4.1) is notable. The paper argues Synthius-Mem has no overfitting risk because "extraction schemas are fixed prompts, the consolidation logic is deterministic, and the retrieval tools are rule-based." This phrasing makes the schemas *fixed prompts* — i.e., the JSON schema is part of the prompt content, which is consistent with OpenAI's `response_format: json_schema` (schema IS the parameter passed to the API, not a learned model). The phrasing also tolerates "fixed prompts + retry-on-validation-failure" as an alternative (consistent with Pydantic + LLM + retry-loop patterns).

4. **No validation-failure handling discussed.** The paper is silent on what happens when structured output fails to validate. Under OpenAI strict-JSON-schema mode, validation is guaranteed by the decoder (failure is impossible by construction). Under Pydantic+retry, failure is handled in application code. Silence here is consistent with strict-mode (because there are no failures to discuss) but does not prove it.
