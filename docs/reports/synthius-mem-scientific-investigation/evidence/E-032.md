## Check (f) — Rollback semantics (reversible diff engine §3.3)

**CRITICAL ISSUE:** MongoDB's transactional model:
- Single-document writes: atomic (no issue).
- Multi-document transactions: supported since v4.0 on replica sets and v4.2 on sharded clusters — **BUT** performance cost is significant on sharded collections, and historical guidance from MongoDB itself discourages heavy multi-doc transaction use.
- The T-002 two-layer envelope requires a consolidation batch to write across all 6 collections atomically per persona (E-048 pattern). MongoDB supports this via `session.startTransaction()`, but:
  - Performance: cross-collection txns add ~2-5× write latency.
  - Sharded clusters require `majority` read concern + `snapshot` isolation — extra config surface.
- **Reversible diff engine** (§3.3): MongoDB lacks native time-travel/point-in-time queries at the application-visible layer (oplog is internal). Implementing the diff engine requires an explicit WAL (E-049-style) layer on top — **not** something MongoDB gives us for free.

This does not outright refute H-032 — multi-doc transactions DO exist and DO support cross-collection atomic commits per persona (E-048 is implementable). But it does show MongoDB offers no native advantage over Postgres for the diff-engine rollback requirement, and Postgres MVCC (E-030) is architecturally simpler for the rollback path.

## Reasoning chain

- DDL/collection layout draftable with `$jsonSchema` validators (closed BSON schema = T-016-compatible).
- Latency arithmetic passes at 200K scale with 4× headroom.
- T-002, T-012, T-016 map 1:1 (envelope, dotted-path indexes, no FK).
- **Weakness:** multi-document transactions required for per-persona consolidation (G-054) are supported but costlier than Postgres — a paper committing to "atomic consolidation per persona" would pick the tool with less operational friction.
- **Weakness:** reversible diff engine (§3.3 / G-021) needs an explicit WAL atop MongoDB — no native point-in-time feature. Postgres + E-049 WAL is cleaner.
- No FAIL clause is cleanly triggered, but H-032 is strictly dominated by H-030 on two architectural axes.
