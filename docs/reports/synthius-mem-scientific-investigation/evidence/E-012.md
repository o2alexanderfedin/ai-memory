## Constructive Argument for Universal Per-Fact Provenance

**Claim 1 (diff engine):** §3.3 says "Memory evolves continuously through a reversible diff engine that supports add, edit, and delete operations with full rollback capability." To roll back a diff, the system must know which extraction call produced the fact being rolled back. This requires `extractor_version` + `extracted_at` on every fact in every domain (not just Biography + Psychometrics).

**Claim 2 (GDPR-erasure, G-060):** GDPR Art. 17 right-to-erasure means a user can request removal of all facts derived from a specific source message (e.g., "delete everything you learned from the message I sent on date X"). This requires `source_message_id` traceability on every fact across all domains. Otherwise, erasure cascades are incomplete.

**Joint requirement:** Both mechanisms require per-fact `source_message_id` + `extracted_at` + `extractor_version`. Restricting provenance to Biography + Psychometrics (as Fig. 2 does) makes Experiences/Preferences/Social/Work either un-erasable or un-rollable — a contradiction with §3.3.

## Conflict Check

No name or semantic clashes.

- All six domain schemas can consume it by $ref with no field-name conflicts.
- Paper's Fig. 2 mentions provenance fields only on Biography + Psychometrics but does NOT commit to exclusion elsewhere.
