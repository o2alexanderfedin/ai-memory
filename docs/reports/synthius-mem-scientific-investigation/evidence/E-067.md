## Arithmetic prong: App. A.1 token budgets

Table 7 (Line 126) itemizes per-message cost: 1K system + 2K retrieved + 1.1K planner + 200 output + 740 extraction = 5,040.

**There is NO consolidation line item in Table 7.** Consolidation cost is NOT reported in App. A.1. This is a significant finding because:

- If consolidation were pure-LLM (H-067), it would be an LLM call per consolidation batch. With N=500 messages, ~200 chunks, and say ~20 consolidation batches (one every ~10 chunks), and ~2-3K tokens per consolidation LLM call (existing_facts + new_facts → merged set), the total consolidation cost would be 20 × 2,500 = ~50K tokens, amortized across 500 msgs = ~100 tok/msg. Not negligible.

- If consolidation were deterministic / rule-based (H-066 with ONLY LLM conflict escalation), the primary cost would be zero LLM tokens; only rare conflicts (say 5% of fact pairs) would trigger a ~500-token LLM call. Amortized cost: ~10-30 tok/msg. Close to the 740 extraction floor but separable.

Table 7's **absence of a consolidation line** is consistent with EITHER H-066 (consolidation cost ~0 or absorbed into the extraction budget) or H-067 (consolidation cost was simply not itemized). However, if H-067 were the design, hiding ~100 tok/msg of LLM cost from a detailed cost table would be odd. The more parsimonious reading is that consolidation cost is negligible → H-066 (primarily deterministic) fits better.

§4.1's "consolidation logic is deterministic" (line 55) is load-bearing because it is the only architectural claim about consolidation's nature. The sentence is part of the "no overfitting" defense, and the reasoning requires consolidation to be NON-learned. An LLM at temperature=0 is still a learned function; the paper's phrasing is more naturally read as "consolidation uses hand-written rules / hashes / deterministic merge policies", not "consolidation uses an LLM at temperature=0".

## Evaluation against criterion

(a) "'Deterministic' claim is load-bearing — i.e., explicitly contrasts with LLM-probabilistic consolidation elsewhere, making a pure-LLM consolidation path architecturally untenable without reinterpretation": **satisfied.** Line 55's three-way parallelism (extraction=prompts, consolidation=deterministic, retrieval=rule-based) specifically contrasts consolidation with the LLM-based extraction, placing it in a non-LLM category. This makes H-067's pure-LLM consolidation reading untenable without reinterpreting "deterministic" as "LLM at temperature=0" — a reinterpretation the paper does not authorize.

(b) "App. A.1 token budgets exclude per-fact LLM consolidation cost at production scale OR include only batchwise consolidation cost (favoring the H-066 hybrid)": **satisfied.** Table 7 has NO consolidation line item. This is compatible with (i) H-066's mostly-deterministic consolidation with negligible amortized LLM cost, or (ii) consolidation cost absorbed into the 740 extraction or 1,100 planner figures. Either reading disfavors H-067's full-LLM-batch consolidation, which would be substantial enough to deserve its own line.

FAIL condition: "'deterministic' can be reinterpreted as 'reproducible given same inputs + seed' (temperature=0) and App. A.1 budgets accommodate pure-LLM batch consolidation": **NOT satisfied.**
- The paper does NOT use "reproducible", "temperature=0", or "seeded" language to reinterpret "deterministic".
- App. A.1 does NOT explicitly accommodate a pure-LLM batch consolidation cost.
- The full-word "deterministic" in a no-overfitting defense is most naturally read in its strict sense (rule-based, hash-based, deterministic-merge-policy) — not as LLM-at-T=0.

## Final verdict

FAIL. H-067 (pure LLM-driven consolidation) is refuted in favor of H-066 (hybrid rule-based + LLM conflict escalation). Three independent lines of evidence:

1. **Load-bearing "deterministic" claim (line 55)**: The paper's no-overfitting defense explicitly categorizes consolidation as "deterministic", in a three-way parallel with "fixed prompts" (extraction) and "rule-based" (retrieval). This places consolidation in the non-LLM category. A pure-LLM interpretation of "deterministic" would undermine the overfitting defense itself.

2. **Absence of consolidation line in Table 7 (App. A.1 cost model)**: If consolidation were pure-LLM, it would consume ~50-100 tok/msg amortized — enough to warrant a line in a detailed cost table. Absence suggests cost is ~0 or trivially small, consistent with primarily deterministic consolidation (H-066's rule-based stages 1-2 dominate, with rare Stage 3 LLM escalation).

3. **Zero hits on softening language**: The paper does not use "reproducible", "temperature=0", or "seeded" — all of which would be the natural reinterpretations for a pure-LLM-but-deterministic-via-T=0 consolidation. The paper means "deterministic" in its strict sense.

H-067 therefore falsifies; H-066 (the hybrid rule-based dedup + LLM conflict escalation model from E-066) remains the architectural reading best supported by paper text.

## Method note + surprising finding

**Surprising finding:** The paper's "deterministic consolidation" claim is a single sentence (line 55), and it is made as part of an overfitting defense, not as a dedicated architectural commitment. The paper does NOT dedicate a subsection to describing how consolidation actually works. This is a significant reproducibility gap — "per-category consolidation (deduplication, merging, conflict resolution)" (line 46) gives the operations, but not the algorithms. A competent engineer reading the paper would still need to invent the hash-based dedup keys, the merge-policy semantics (confidence = max vs. sum vs. average?), and the conflict-resolution escalation triggers — which is exactly what H-066 attempts to construct. This gap is distinct from H-067's falsification and deserves its own follow-up (likely G-??? — "consolidation algorithm underspecified").
