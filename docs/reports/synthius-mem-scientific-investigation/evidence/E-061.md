## Drafted Artifacts

### 1. Retry wrapper with exponential backoff

```python
import asyncio, random, logging
from typing import Callable, Awaitable

BASE_DELAY = 0.5   # seconds
FACTOR = 2.0
MAX_ATTEMPTS = 3

class TransientError(Exception): pass    # 429, 5xx, timeout
class SchemaViolation(Exception): pass   # strict-mode rarely raises, but possible on unsupported schema features
class PermanentError(Exception): pass    # 4xx auth, input validation

async def with_retry(call: Callable[[], Awaitable], op_name: str):
    for attempt in range(1, MAX_ATTEMPTS + 1):
        try:
            return await call()
        except TransientError as e:
            if attempt == MAX_ATTEMPTS:
                raise
            delay = BASE_DELAY * (FACTOR ** (attempt - 1)) * (1 + random.uniform(-0.1, 0.1))
            logging.warning(f"{op_name} transient failure (attempt {attempt}); sleeping {delay:.2f}s")
            await asyncio.sleep(delay)
        except SchemaViolation:
            raise   # no retry — deterministic fail
        except PermanentError:
            raise
```

Backoff schedule: 0.5s → 1.0s → 2.0s (max cumulative wait ~3.5s before DLQ).

### 4. Re-run at next consolidation cycle

```python
def consolidation_preflight(persona_id):
    pending_dlq = dlq_fetch_ready(persona_id, now=iso_now())
    for entry in pending_dlq:
        try:
            chunk = chunks_fetch(entry.chunk_id)
            facts = await with_retry(
                lambda: extract_domain(chunk, entry.domain, persona_id),
                f"retry-dlq:{entry.domain}")
            upsert_domain_facts(persona_id, chunk.id, entry.domain, facts)
            dlq_mark_resolved(entry)
```

## Checks performed

**(a) Exponential backoff, max 3 attempts, base 500ms, factor 2:** Matches spec; backoff schedule (0.5s, 1.0s, 2.0s) produces maximum per-call wait ~3.5s before DLQ commit. ✓

**(b) DLQ entry schema:** Contains `persona_id`, `chunk_id`, `domain`, `error_class`, `last_attempt_ts` + extras for idempotent replay. ✓

**(c) Partial-accept per-chunk:** 5/6 successful domains are persisted in the chunk's single transaction; the failing domain is flagged in DLQ. The commit granularity is per-chunk, not per-consolidation-batch. This preserves T-032 (per-persona single transaction) at consolidation-write time because:

- Extraction-write is a different persistence event than consolidation-write.
- At consolidation time, the WAL+snapshot cycle (T-033) operates over the already-extracted facts in their 6 tables; that stage is atomic per the T-032 rule.
- The chunk-level partial commit is at the *extraction* stage, where the unit of atomicity is the chunk (not the persona×all-domains batch).

This interpretation matches the paper's silence on per-chunk atomicity and is consistent with "deterministic consolidation" at the consolidation stage. ✓

**(d) H-060 strict-JSON rarity of schema violations:** Under OpenAI strict-mode JSON Schema, malformed output is effectively impossible (the decoder enforces it). Retry path primarily handles transport-layer issues (429 rate limiting, 502/503/504 server errors, socket timeouts). ✓

## Reasoning

- Retry-with-exponential-backoff wrapper drafted with standard 3-attempt schedule, jitter to avoid thundering-herd.
- DLQ entry schema is complete for resurrection at next consolidation cycle; idempotent via unique `(persona_id, chunk_id, domain)` key.
- Partial-accept policy is coherent: per-chunk txn covers the 5 successful domains; failing domain's data is NOT written, and is retried asynchronously.
- H-060 strict-JSON mode reduces schema-violation incidence to near-zero; the retry path's load-bearing case is transport failures.
- The chunk-level atomic commit does NOT conflict with T-032's per-persona single-transaction rule, because T-032 applies at consolidation-write time (snapshot materialization), not extraction-write time.
- 21.79 ms retrieval SLO is preserved because DLQ is write-path-only.
