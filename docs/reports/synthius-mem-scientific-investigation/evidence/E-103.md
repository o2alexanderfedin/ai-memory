## Design — production rate-limit architecture

### 1. Layered queues

```
    ┌──────────────────────────┐
    │  Tenant admission (L1)    │  ← OpenAI TPM/RPM / tenant
    │  token bucket             │     capped at Tier N quota
    └───────────┬──────────────┘
                │
    ┌───────────▼──────────────┐
    │  Persona admission (L2)   │  ← per-persona fairness
    │  token bucket              │     10K tok/min default
    └───────────┬──────────────┘
                │
    ┌───────────▼──────────────┐
    │  Provider-layer retry     │  ← T-041 DLQ / Retry-After
    │  (exponential back-off)   │     exponential back-off
    └──────────────────────────┘
```

### 2. Per-tenant token bucket (L1)

Sized to OpenAI quota (public as of 2026, 4.1-mini):
- Tier 1: 200K TPM, 500 RPM
- Tier 2: 2M TPM, 5K RPM
- Tier 3: 4M TPM, 5K RPM
- Tier 4: 10M TPM, 10K RPM
- Tier 5: 150M TPM, 30K RPM

Implementation:
```python
class TenantBucket:
    refill_rate = tier_tpm / 60  # tokens/sec
    burst_cap = 2 * refill_rate * 60  # 2-min burst
    tokens: float = burst_cap
    last_refill: float
    
    def take(self, n_tokens: float) -> bool:
        self._refill()
        if self.tokens >= n_tokens:
            self.tokens -= n_tokens
            return True
        return False  # 429 upstream
```

### 3. Per-persona fairness (L2)

```python
class PersonaBucket:
    default_refill = 10_000 / 60  # 10K tokens/min per persona
    burst_cap = 60_000            # 6 minutes of burst
    
    # Enterprise personas get higher quota:
    tier_override: Dict[str, int] = {
        "celebrity": 60_000,  # 60K tokens/min
        "bot": 100_000,
    }
```

### 4. Admission vs retry separation

Admission control (L1 + L2) decides **whether** to dispatch.
Retry policy (L3) decides **how** to recover from downstream failures (transient 429 from OpenAI, 5xx, timeout).

```
if L1.take(n) and L2.take(n):       # admission
    try:
        resp = openai.call(...)
    except RateLimitError as e:      # retry loop, not admission
        sleep(parse_retry_after(e.headers))
        retry with exp back-off up to 3x
        if still_failing:
            push to T-041 DLQ
```

This separation is critical: admission control **prevents** load that would otherwise generate retries; retry policy handles unavoidable transient errors. Mixing the two creates cascading failure modes.

### 5. Retry-After header honoring

Per OpenAI docs, on 429, headers include `Retry-After` and `x-ratelimit-reset-*`. Implementation:
```python
def parse_retry_after(headers) -> float:
    if "Retry-After" in headers:
        return float(headers["Retry-After"])
    # fallback: exp back-off with jitter
    return random.uniform(2**attempt, 2**(attempt+1))
```

### 6. Worked example — noisy neighbor burst

Setup: 100 personas share a Tier-4 tenant (10M TPM). One persona bursts 100 consecutive consolidation cycles at 30K tokens each = 3M tokens in ~1 minute.

**Without per-persona bucket (just L1):**
- L1 admits 3M tokens from the hot persona → consumes 30% of 10M TPM in 1 minute.
- Quota mostly consumed by hot persona.
- Other 99 personas experience elevated latency but don't hard-fail (L1 still has some capacity).

**With per-persona bucket (L1 + L2):**
- L2 throttles hot persona at 10K tok/min → hot persona gets 1 consolidation cycle every ~3 minutes.
- 3M tokens spread over 300 minutes (5 hours).
- Remaining 99 personas unaffected; L1 has full 10M TPM for other traffic minus the hot persona's 10K/min.
- Hot persona's work eventually completes; no data loss. ✓

### 7. OpenAI quota references

Public docs (https://platform.openai.com/docs/guides/rate-limits):
- TPM = Tokens Per Minute (input + output combined)
- RPM = Requests Per Minute
- Different tiers by org spend: scales from 200K TPM (Tier 1) to 150M TPM (Tier 5).
- On 429: must back off per Retry-After; typical window 20-60 seconds.

### 8. Compatibility with 94.37% accuracy claim

Rate-limit handling does NOT interact with correctness. 429 responses are retried transparently; no answer is degraded by throttling. The 94.37% accuracy claim is unaffected. The only user-visible effect is **latency** under heavy load — which is the intended tradeoff of fairness.
