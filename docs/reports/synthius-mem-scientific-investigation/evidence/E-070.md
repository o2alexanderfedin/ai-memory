# E-070 Evidence — H-070 Planner is a distilled classifier (not an LLM)

OUTCOME: FAIL

## Pass/Fail criterion (verbatim)

> PASS iff WebFetch on Synthius.ai + WebSearch for `"Synthius" planner` / `"Synthius-Mem" classifier` / `"Synthius-Mem" router` + authors' (Gadzhiev, Kislov) prior work returns (a) any evidence of a distilled-classifier or logistic-regression planner architecture (favoring H-070), OR (b) silence + no contradiction. FAIL if external evidence (Synthius.ai blog, GitHub, authors' commentary) explicitly names an LLM-based planner (favoring H-069), OR if App. A.1's 1,100-token planner budget is confirmed load-bearing for Synthius-Mem itself (not a baseline comparison — refuting the classifier-only reinterpretation), OR if planner output is documented to require free-form query rewriting (per T-027) that a classifier cannot produce.

## Search strategy

Three-pronged external-evidence search:
1. **WebFetch on synthius.ai** asking specifically about planner/router architecture, classifier vs LLM, and 6-tool catalog.
2. **WebSearch** for "Synthius-Mem planner classifier router", "Synthius.ai memory CategoryRAG planner LLM", and "classifier-based planner memory system routing" / "distilled classifier retrieval planner" / "logistic regression domain routing agent memory".
3. **WebSearch** for comparable systems (Mem0, TiMem, MemMachine) to see whether classifier-based planners are the dominant architecture in this family.

## Evidence gathered

### Prong 1: Synthius.ai page (WebFetch, verbatim)

The WebFetch returned these explicit statements from synthius.ai:

> "A **planner picks which domains matter for the query**" during the retrieval phase
> "**Planner LLM** ... Reads the user message, picks which domains matter."
> "Tools fetch only the relevant facts from the selected domain stores — bounded, cheap, and fast."

Classification: **Synthius.ai explicitly names the planner as an LLM** — "Planner LLM". This is a direct, author-voiced architectural commitment, and it directly contradicts H-070's distilled-classifier claim.

The page also lists the six domains (Biography, Experiences, Preferences, Social Circle, Work, Psychometrics) and describes the approach as "Category-aware retrieval by domain" in contrast to "similarity search across everything" — consistent with the paper's §3.3 description but without adding implementation details about the planner's model class.

### Prong 2a: WebSearch for "Synthius-Mem planner classifier"

Top hits returned the arxiv paper itself (2604.11563) and related general routing literature. No hit confirmed a classifier-based planner for Synthius-Mem. One hit (emergentmind.com "Persona-Driven Memory Architecture") is indexed but not a primary source.

### Prong 2b: WebSearch for "classifier-based planner memory system routing" / "distilled classifier retrieval planner"

Returned general literature on LLM routing (RouteLLM, DistilBERT classifiers for LLM selection, BERT-based routing for cost reduction). None of these hits are Synthius-specific; they describe the alternative architecture class (distilled classifier routing) as a GENERAL approach in the literature, but none attaches this architecture to Synthius-Mem specifically.

Relevant context from the general literature:
- RouteLLM (Ong et al.) trains DistilBERT classifiers for LLM selection with 30% cost reduction.
- LLM-based routing is substantially more common in persona-memory systems (Mem0, TiMem, MemMachine all use LLM-based routing per Prong 3).

### Prong 3: Comparable systems (Mem0, TiMem, MemMachine planner architectures)

WebSearch revealed:
- **Mem0**: "rather than using a separate classifier, **Mem0 leverages the LLM's reasoning capabilities** to directly select the appropriate operation"
- **TiMem**: "**two LLM calls per query**: a recall planner (1 call) and recall gating (1 call)"
- **MemMachine**: "evaluates a **Retrieval Agent** that routes queries to direct retrieval, parallel decomposition, or iterative chain-of-query strategies" — Agent implies LLM-based routing.

Classification: **The dominant architecture class in Synthius-Mem's peer group is LLM-based planning, not classifier-based.** If Synthius-Mem uniquely used a distilled classifier, it would be a distinguishing architectural choice worth highlighting in the paper — but neither the paper nor synthius.ai highlights this. The simplest reading (and the one synthius.ai explicitly confirms) is that Synthius-Mem follows the peer-group pattern: LLM-based planner.

### App. A.1 planner budget (load-bearing check)

From the paper (Line 126, App. A.1 Table 7):
> "Synthius-Mem ~2,000 tok retrieved + **1,100 tok planner** | 740 tok extraction | ~5,040"

And line 91 (§4.5):
> "Synthius-Mem uses approximately 5,040 tokens per message at N=500: 1K system prompt + 2K retrieved structured context + **1.1K planner LLM call** + 200 output + 740 tokens of amortized one-time extraction"

Classification: **Line 91 explicitly calls it a "1.1K planner LLM call"** — a direct phrase attaching "LLM" to the planner's 1,100-token budget. This is decisive: the paper itself calls the planner an LLM (§4.5), and App. A.1's cost model allocates 1,100 tokens to that LLM call as part of Synthius-Mem's per-message budget (NOT a baseline comparison). The 1,100-token budget is load-bearing.

This triggers the FAIL condition: "App. A.1's 1,100-token planner budget is confirmed load-bearing for Synthius-Mem itself (not a baseline comparison)". The criterion's own prose anticipates this falsification route.

## Evaluation against criterion

PASS prong (a) "any evidence of a distilled-classifier or logistic-regression planner architecture": **NOT satisfied.** Zero Synthius-specific hits support a classifier-based planner. Related-work hits describe classifier routing as a general technique, but none attach it to Synthius-Mem.

PASS prong (b) "silence + no contradiction": **NOT satisfied.** There is explicit contradiction: synthius.ai says "Planner LLM" and the paper (§4.5, line 91) says "planner LLM call" with 1,100-token budget.

FAIL condition 1: "external evidence explicitly names an LLM-based planner": **TRIGGERED.** Synthius.ai's page says "Planner LLM ... Reads the user message".

FAIL condition 2: "App. A.1's 1,100-token planner budget is confirmed load-bearing for Synthius-Mem itself": **TRIGGERED.** Paper line 91 says "1.1K planner LLM call" as part of Synthius-Mem's per-message cost breakdown.

FAIL condition 3: "planner output is documented to require free-form query rewriting": Not directly confirmed, but the LLM-based planner hypothesis (H-069) accommodates free-form rewriting naturally.

Two out of three FAIL triggers fire. H-070 is falsified.

## Final verdict

FAIL. H-070 (classifier-based planner) is refuted by both (i) direct external evidence from Synthius.ai's own page explicitly naming "Planner LLM", and (ii) paper text (line 91, §4.5) calling the planner a "1.1K planner LLM call" as part of Synthius-Mem's production cost model — not a baseline comparison. The 1,100-token budget allocated to the planner is LLM-scale, not classifier-scale (a distilled classifier would cost <10ms and effectively zero tokens since it operates on raw text inputs, not via a tokenized LLM-prompt interface).

H-070's one plausible remaining interpretation was that "1,100-token planner" in App. A.1 referred to a baseline comparison. This interpretation is refuted by line 91's direct attribution of the 1,100 tokens to Synthius-Mem itself.

Thus H-069 (LLM-based planner, GPT-4.1-mini with few-shot routing prompt) is strongly supported as the winning hypothesis in the H-069 / H-070 pair.

## Notable findings and caveats

1. **Direct external confirmation**: Synthius.ai's own page (crawled 2026-04-20) explicitly labels the planner "Planner LLM". This is the strongest form of external-evidence resolution — author-voiced architectural commitment matching a specific paper claim.

2. **Peer-system pattern consistency**: Mem0, TiMem, MemMachine all use LLM-based planners. Synthius-Mem following the peer pattern with its own LLM planner is parsimonious.

3. **1,100-token budget decisive**: The paper line 91's "1.1K planner LLM call" is a single-sentence resolution that by itself refutes H-070 independently of external evidence. The external evidence confirms; the paper text, on careful reading, already commits.

4. **Caveat on external evidence date**: The WebFetch captured synthius.ai's public site at the time of this run (2026-04-20). The page's content may have been updated to match the arxiv paper's architecture descriptions; it is possible that Synthius.ai's marketing page was authored after the paper and simply mirrors the paper's "planner LLM" framing. This is a minor caveat — even if synthius.ai's description is derivative of the paper, the paper text itself (line 91) is sufficient to resolve H-070.

5. **Model identity still underdetermined**: Synthius.ai says "Planner LLM" but does not name the planner model. The paper (§4.4) names GPT-4.1-mini as answer + judge, and by implicit same-family reasoning the planner is likely also GPT-4.1-mini (H-069's claim). But external evidence does not explicitly confirm the model identity — future wave could dig into the Synthius platform blog or GitHub for a definitive statement.
