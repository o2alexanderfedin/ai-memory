## Arithmetic prong: 21.79 ms ⊥ LLM/embedding calls

Per-query latency budget for CategoryRAG (Fig. 7, §4.6): 21.79 ms mean.

Minimum per-query costs for candidate primitives:
- **GPT-4.1-mini first-token latency** (per published OpenAI + third-party measurements, and consistent with the answer/judge model the paper uses): typically 400–1,200 ms first-token, and no single-token response would be sufficient (the LLM would have to emit a classification token at least). Floor of ≈500 ms.
- **OpenAI text-embedding-3-small API roundtrip** (the embedding model the paper uses FOR THE BASELINE): median latency ≈50–150 ms per call from US datacenter POPs, floor ≈100 ms. Local encoders would need a GPU roundtrip (tens of ms plus cold-start overhead).
- **Any network call** to Pinecone/Weaviate: 15–20 ms floor per paper line 104 — that is the LOWER bound just for the vector-DB probe, before any embedding computation.

21.79 ms < 100 ms (embedding) < 500 ms (LLM) by ≥5× and ≥22× respectively. A CategoryRAG internal step involving an LLM call or an external embedding call would shift the mean well above the published 21.79 ms. The budget is only consistent with in-process, in-memory, deterministic matching primitives (exact match on typed fields, hash lookup, B-tree/GIN probe — all sub-millisecond).

Conversely, Synthius-Mem's own published overhead table (Table 7, Line 126) accounts for extraction (amortized), planner (1,100 tokens), and retrieved context (2,000 tokens). It does NOT budget a per-query embedding call or a per-query LLM judge inside the retrieval path — consistent with "field-level matching" from §3.3.
