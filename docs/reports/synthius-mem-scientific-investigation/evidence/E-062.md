## Arithmetic prong: App. A.1 Table 7 cost structure

Table 7 (Line 126):
> "Synthius-Mem ~2,000 tok retrieved + 1,100 tok planner | **740 tok extraction** | ~5,040"

The 740 tok/msg is **amortized across the conversation**, not per-call. Line 91 clarifies:
> "Synthius-Mem uses approximately 5,040 tokens per message at N=500: 1K system prompt + 2K retrieved structured context + 1.1K planner LLM call + 200 output + **740 tokens of amortized one-time extraction (370K extraction tokens divided across 500 messages)**."

So the total extraction cost per conversation = 370K tokens. At N=500 messages, that's 740 tok/msg amortized. If each chunk covers ~2-3 messages (per H-052's 2K-window chunker with dialog-turn preservation), there are ~200 chunks per 500-message conversation. 370K / 200 chunks = ~1,850 tokens/chunk of extraction cost.

For 6 concurrent per-domain calls with a ~2K-token chunk input + ~300-500 tokens of per-domain schema/instructions + ~100-200 tokens of per-domain output:
- Per-call input: ~2,000 (chunk) + 400 (schema) = ~2,400 input tokens.
- Per-call output: ~150 tokens.
- 6 calls × 2,400 input = 14,400 input tokens/chunk.
- 6 calls × 150 output = 900 output tokens/chunk.

That's ~15,300 tokens/chunk total × 200 chunks = 3,060,000 tokens across the conversation, or ~6,100 tok/msg. This is **higher** than the paper's 370K / 500 = 740 tok/msg — off by ~8×.

But App. A.1's framing ("740 tok extraction amortized") may exclude the system-prompt portion (which is the shared schema context that OpenAI's strict-JSON mode can cache — OpenAI offers 50% input-caching discount for repeated prompts). Alternative reading: if the extraction runs one call per chunk per domain but the shared schema is cached (50% discount), the effective extraction cost drops to ~7,650 effective tokens/chunk × 200 chunks / 500 msgs ≈ ~3,060 tok/msg — still higher than 740.

A cleaner arithmetic: 740 tok/msg × 500 msg = 370,000 tokens total. 370K / 6 domains = ~62K per domain total. 62K / 200 chunks = ~310 tokens per domain per chunk. That's only ~310 tokens per per-domain-per-chunk extraction call — far too small for a realistic extraction call (chunk input alone is 2K tokens).

This tension suggests EITHER:
(a) The 740 tok/msg figure is NOT a complete per-message extraction cost — it may be the NET additional cost after caching / batching optimizations. OpenAI's Batch API provides 50% discount; prompt caching provides 50% on repeated input. A factor of 4× optimization is plausible.
(b) The 740 tok/msg figure counts only OUTPUT tokens (not input), since output tokens are ~10× more expensive and are the typical throughput-limiting factor.
(c) The 740 figure assumes Synthius-Mem compresses chunks significantly before extraction (not supported by §3.3 text).

None of these readings contradict the 6-parallel hypothesis — they all apply equivalently to a single-multi-schema call. The arithmetic does not discriminate.

### Alternative: single multi-schema call

A single multi-schema call would have:
- Input: ~2,000 (chunk) + ~2,000 (all 6 schemas concatenated into one prompt) = ~4,000 tokens.
- Output: ~900 tokens (all 6 domains in one response).
- Per-chunk: ~4,900 tokens × 200 chunks = ~980K tokens / 500 msgs ≈ ~2,000 tok/msg.

Still off from 740, but *closer*. A single-multi-schema reading fits the numbers marginally better than 6 parallel calls, but not decisively so given the caching/batching uncertainties.

## Final verdict

PASS. H-062 (6 concurrent per-domain LLM calls per chunk) is supported by (i) the plural "structured output schemas" phrasing (line 46) co-occurring with "parallel" + "all six domains"; (ii) the Figure 1 caption (line 21) explicitly stating "parallel domain extraction across six cognitive domains"; (iii) zero paper hits committing to multi-domain joint decoding, a single schema, or multi-domain fan-in; (iv) the arithmetic (App. A.1) being compatible with 6 additive calls under standard OpenAI Batch API / prompt-caching discounts.

The evidence is not airtight — the paper could be clearer, and a skeptical reading could accommodate a single multi-schema call. But the weight of linguistic evidence (plural "schemas", "parallel", "all six domains") favors 6-parallel-calls over any alternative.

## Notable findings

1. **"Parallel" is used twice, both in positions consistent with fan-out.** Figure 1 caption (line 21) says "parallel domain extraction across six cognitive domains"; §3.3 (line 46) says "parallel LLM-based extraction into all six domains". Both phrasings naturally read as "one per domain, in parallel".

2. **The paper never uses "concurrent" or "fan out".** While these are idiomatic for the 6-parallel reading, the paper consistently prefers "parallel". This is a minor phrasing inconsistency that does not change the semantic reading.

3. **Prompt caching / Batch API discount ambiguity.** The 740 tok/msg amortized extraction cost is ambiguous. OpenAI's Batch API provides 50% discount; prompt caching provides 50% on cached repeated input; both apply naturally to the extraction workload (6 per-domain calls per chunk × many chunks). If the 740 number includes these discounts, the "effective raw token cost" would be 2-4× higher (~1,500–3,000 tok/msg), which matches the expected cost of 6 × ~300 output tokens/chunk × 200 chunks / 500 msgs. Paper does not clarify which discounts are baked into the 740 number, which is a reproducibility gap.

4. **Single-multi-schema call would be architecturally unusual.** OpenAI's strict-JSON-schema mode (line 46 "structured output schemas") is designed for a single response_format per call. A multi-schema "discriminated union" call is possible but not the default pattern. The plural "schemas" in line 46 is most naturally aligned with OpenAI's default per-call API usage.
