## Drafted Layout

### Per-persona file: `/personas/<persona_id>.sqlite`

```sql
-- Six domain tables, mirroring the 6 JSON files bullet literally.
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = OFF;  -- T-016

CREATE TABLE biography (
  fact_id        TEXT PRIMARY KEY,
  schema_version TEXT NOT NULL,
  fields         TEXT NOT NULL,  -- JSON1 ext. SQLite 3.38+ supports json_extract indexes
  envelope       TEXT NOT NULL,
  created_at     INTEGER NOT NULL,
  updated_at     INTEGER NOT NULL
);
CREATE INDEX idx_bio_institution ON biography (json_extract(fields,'$.institution'));
CREATE INDEX idx_bio_year        ON biography (CAST(json_extract(fields,'$.year') AS INTEGER));

CREATE TABLE experiences (
  fact_id TEXT PRIMARY KEY,
  schema_version TEXT NOT NULL,
  fields TEXT NOT NULL, envelope TEXT NOT NULL,
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL
);
CREATE INDEX idx_exp_parent ON experiences (json_extract(fields,'$.parent_event_id'));

CREATE TABLE preferences (
  fact_id TEXT PRIMARY KEY,
  schema_version TEXT, fields TEXT, envelope TEXT,
  created_at INTEGER, updated_at INTEGER
);
CREATE INDEX idx_pref_target ON preferences (json_extract(fields,'$.target'));

CREATE TABLE social_circle (
  fact_id TEXT PRIMARY KEY,   -- = person_id
  schema_version TEXT, fields TEXT, envelope TEXT,
  created_at INTEGER, updated_at INTEGER
);
-- JSON array indexing via generated column
ALTER TABLE social_circle ADD COLUMN primary_name TEXT
  GENERATED ALWAYS AS (json_extract(fields,'$.names[0]')) STORED;
CREATE INDEX idx_soc_name ON social_circle(primary_name);

CREATE TABLE work (
  fact_id TEXT PRIMARY KEY,
  schema_version TEXT, fields TEXT, envelope TEXT,
  created_at INTEGER, updated_at INTEGER
);
CREATE INDEX idx_work_employer ON work (json_extract(fields,'$.employer'));

CREATE TABLE psychometrics (
  fact_id TEXT PRIMARY KEY,
  schema_version TEXT, fields TEXT, envelope TEXT,
  created_at INTEGER, updated_at INTEGER
);
CREATE INDEX idx_psy_fw ON psychometrics (
  json_extract(fields,'$.framework'),
  json_extract(fields,'$.trait')
);
```

### Global tenant-index DB: `/tenants.sqlite`

```sql
CREATE TABLE personas (
  persona_id    TEXT PRIMARY KEY,   -- ULID or UUIDv4
  storage_path  TEXT NOT NULL,
  created_at    INTEGER NOT NULL,
  last_access   INTEGER,
  size_bytes    INTEGER,
  gdpr_erase_at INTEGER              -- NULL unless scheduled
);
CREATE INDEX idx_personas_last_access ON personas(last_access);
```

Lookup path: `SELECT storage_path FROM personas WHERE persona_id=?` → open per-persona file → query.

## Check (a) — Fig. 2 examples serialize verbatim

Same as E-030: each Fig. 2 datum serializes into `fields` JSON. SQLite's JSON1 extension + generated columns + `json_extract` indexes provide equivalent query capability to Postgres JSONB for single-value lookups. ✓

## Check (b) — T-002 + T-012 compatibility

- **T-002 two-layer envelope:** outer layer is the persona SQLite file (carries `persona_id` implicitly via filename + `tenants.personas`); inner layer is the `facts[]` array realized as table rows.
- **T-012 typed fields:** each queryable sub-field exposed via JSON-extract index; indexed atomic values retrieve in log-N. ✓

## Check (c) — Latency arithmetic

- Per-persona scale: 500 MB / ~200 personas ≈ **2.5 MB per persona**, ≈ 2,000 facts (6 domains × ~330 facts).
- B-tree probe: log2(2,000) ≈ 11 comparisons × 100 ns (SQLite in page cache) = **~1.1 µs**.
- Open-file overhead: first access ~200 µs (mmap), cached after.
- Global tenant-index lookup: log2(200) ≈ 7.6 comparisons × 100 ns = **~0.8 µs**.
- Total hot path: **< 1 ms**, 20×+ headroom vs 21.79 ms. ✓

## Check (d) — GDPR Art. 17 crypto-shred

`rm /personas/<persona_id>.sqlite && DELETE FROM personas WHERE persona_id=?` — atomic, one-file-delete. No residual cross-persona references (T-016). ✓

## Check (e) — Scaling

500 MB / 200 personas / 6 domains ≈ 400 KB per domain file if per-domain (rejected), or 2.5 MB per persona (chosen). File system handles 200 files trivially; many systems handle 1M files fine. ✓
