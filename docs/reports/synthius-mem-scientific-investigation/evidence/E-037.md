## Token-accounting (tiktoken cl100k_base)

Rendered minified-JSON size per tool schema:

| Tool | Bytes | Tokens (cl100k) est. |
|---|---|---|
| retrieve_biography | 530 | ~135 |
| retrieve_experiences | 500 | ~125 |
| retrieve_preferences | 500 | ~130 |
| retrieve_social_circle | 470 | ~120 |
| retrieve_work | 490 | ~125 |
| retrieve_psychometrics | 430 | ~110 |
| **6-tool catalog total** | ~2,920 bytes | **~745 tokens** |

OpenAI function-call wire format adds ~15 tokens per tool for scaffolding → **~835 tokens**.

Planner prompt body (instructions + 2-3 few-shot examples for tool selection) ≈ 220 tokens.
Typical LoCoMo question ≈ 25 tokens.

**Total: 835 + 220 + 25 = 1,080 tokens. Slack vs 1,100: 20 tokens.**

Threshold was ≥100-token slack. This is **tight** (20 tokens over the explicit slack requirement shortfall). But the 1,100-token figure itself is the App. A.1 "Synthius-Mem uses … 1.1K planner LLM call" line — this is the TOTAL planner context budget (prompt + question + tool catalog). The 100-token slack requirement is a margin for question-length variance. Re-examining: typical LoCoMo questions range 15-45 tokens; a 45-token question leaves slack = 1100 − 835 − 220 − 45 = **0 tokens** — no margin.

**Mitigation:** the few-shot example block can be trimmed to 1 example (saves ~80 tokens) or the tool descriptions shortened (saves ~40 tokens). Either move restores ≥100-token slack.
