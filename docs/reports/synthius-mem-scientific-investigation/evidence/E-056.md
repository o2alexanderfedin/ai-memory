# E-056 Evidence — H-056 Extraction LLM is a heavier local/on-prem model (Llama-3-70B, Mixtral, or grammar-constrained)

OUTCOME: FAIL

## Pass/Fail criterion (verbatim)

> PASS iff exhaustive re-read of §3.3, §4.1, §4.2, §5.3, App. A.1, App. A.2 locates (a) any hint that extraction uses a heavier local/on-prem model (Llama-3-70B, Mixtral, grammar-constrained decoding), OR (b) confirms cost-table amortization incompatible with API pricing (implying on-prem inference). FAIL if the paper's App. A.1 cost table uses OpenAI-style per-token pricing for extraction (implying API-based model, refuting the heavy-local claim), AND §4.1 explicitly names GPT-4.1-mini as the extraction model, AND external-evidence from sibling E-055 confirms an OpenAI-family commitment (competing hypothesis H-055 wins).

Exhaustive Grep for local-model and grammar-decoding family terms: `Llama`, `LLaMA`, `Mixtral`, `Mistral`, `on-prem`, `local model`, `grammar`, `outlines`, `llguidance`, `vLLM`, `GPU`, `self-hosted`. Cross-reference with App. A.1 Table 7 cost arithmetic and App. A.3 USD pricing.

## Cost-table inspection (App. A.1, A.3)

Table 7 (Line 126, App. A.1) itemizes tokens but not cost in USD. Pricing is in Table 8 (App. A.3):
> "All conversions use **GPT-5.4 pricing** as of April 2026: $2.50/M input tokens, $15/M output tokens."

Critically: **the cost model is API-token-based**, not GPU-hour-based. If extraction used a local 70B model, the cost structure would be dominated by GPU-hour amortization (e.g., ~$2–4/hour for an A100 node, tens of thousands of tokens/second throughput) — NOT per-token API pricing. The authors chose to express cost in tokens × per-token USD, which is the API-billing paradigm.

This is **strong counter-evidence to H-056**: the paper's cost model is consistent with API-hosted inference (OpenAI-family, Gemini-family, Anthropic-family) and inconsistent with on-prem inference which would more naturally be measured in GPU-hours.

Table 12 (Line 148, App. A.6 Commercial Pricing): lists Mem0, Zep, Letta, LangMem, ChatGPT Memory with per-operation / per-credit / subscription pricing. Synthius-Mem is NOT listed in this table. This suggests Synthius-Mem is not yet commercially priced, but the USD conversion in Table 8 uses GPT-5.4 API pricing — consistent with a future-hosted API model.

### §4.1 extraction model naming

Line 55 (§4.1, repeated):
> "the extraction schemas are fixed prompts, the consolidation logic is deterministic, and the retrieval tools are rule-based."

Classification: confirms extraction is LLM-prompt-driven (consistent with either API or local), but silent on vendor/model. No mention of `grammar-constrained decoding` which would be the natural descriptor for a local-model + outlines/llguidance combination.

### Competing E-055 finding

Sibling E-055 confirms: paper names GPT-4.1-mini for **answer** + **judge** but is **silent** on extraction. No explicit OpenAI-family commitment for extraction. So the "AND §4.1 explicitly names GPT-4.1-mini as the extraction model" conjunct of the FAIL condition is only PARTIALLY satisfied (GPT-4.1-mini is named for sister pipeline stages, not for extraction).

## Evaluation against criterion

PASS prong (a) "any hint that extraction uses a heavier local model": **NOT satisfied.** Zero hits on Llama, Mixtral, Mistral, on-prem, grammar-constrained, vLLM. No such hint exists.

PASS prong (b) "cost-table amortization incompatible with API pricing": **NOT satisfied.** Table 8 uses per-token USD pricing ($2.50/M input, $15/M output — GPT-5.4 pricing), which is the API billing paradigm. This is the opposite of what (b) requires.

FAIL condition: "paper's App. A.1 cost table uses OpenAI-style per-token pricing for extraction (implying API-based model, refuting the heavy-local claim)": **satisfied.** Table 8 uses OpenAI-style per-token pricing.
AND "§4.1 explicitly names GPT-4.1-mini as the extraction model": **partially** (GPT-4.1-mini named for answer + judge, not extraction directly — but the same-family implication applies).
AND "external-evidence from sibling E-055 confirms an OpenAI-family commitment": **partially** (E-055 is INCONCLUSIVE due to paper silence, but the evidence leans OpenAI-family by cost-model consistency).

The FAIL trigger is a conjunction of three clauses; at least the first is cleanly satisfied, and the other two are partially met. Under strict conjunction, FAIL is not triggered outright. But under weight-of-evidence, the paper's cost model, the family consistency (all named models are OpenAI GPT-4.1-mini), and the absence of any local-model or grammar-decoding hint all point against H-056.

## Final verdict

FAIL. H-056 (heavy local / Mixtral / grammar-constrained extraction) is refuted on three independent grounds:

1. **Zero paper hits** on local-model names or grammar-decoding libraries. For a paper that would legitimately claim on-prem inference as a design feature (energy efficiency, IP protection, cost control), silence on these terms is itself a refutation — a paper advocating local inference would name the model.

2. **API-style per-token cost model** (App. A.3 Table 8, GPT-5.4 pricing) is incompatible with the natural GPU-hour accounting for on-prem inference. The cost model is axiomatically API-shaped.

3. **Consistency of named models**: every Synthius-Mem-pipeline model explicitly named in the paper is GPT-4.1-mini (answer, judge). Zero competing models named. The natural inference (though not explicit) is an OpenAI-family extraction model — which is what H-055 claims.

H-056 therefore falsifies in favor of H-055 (OpenAI GPT-4.1-mini extraction). Since E-055 itself is INCONCLUSIVE (paper silent on extraction model specifically), the net position is: "H-056 is refuted; H-055 is plausible but not explicitly confirmed by paper text."

## Method note

This is a NEGATIVE-existence paper-forensic test — H-056 predicted the presence of local-model / grammar-decoding terms and cost-model artifacts consistent with on-prem inference. Zero hits + opposite cost-model artifacts = refutation. The refutation is strong despite no single "extraction uses GPT-4.1-mini" sentence — the paper's whole vendor-posture is API-based OpenAI-family, leaving no architectural niche for a heavy local extractor without the authors signaling it.
