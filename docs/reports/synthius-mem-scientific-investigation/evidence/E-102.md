## Design — per-persona LRU cache

### 1. Cache structure

```python
class PersonaCache:
    # Key: (persona_id, domain)
    # Value: (epoch, List[FactItem])
    cache: OrderedDict[Tuple[str, str], Tuple[int, List[FactItem]]]
    max_entries: int = 6000  # 1000 personas × 6 domains

class PersonaEpoch:
    # Bumped by consolidation commit per T-032
    current: Dict[persona_id, int]
```

### 2. Read path

```
def retrieve(persona_id, domain, query_plan):
    expected_epoch = epoch_store.get(persona_id)
    cached = cache.get((persona_id, domain))
    if cached and cached.epoch == expected_epoch:
        return filter(cached.facts, query_plan)          # HIT
    facts = storage.query(persona_id, domain)             # MISS
    cache.put((persona_id, domain), (expected_epoch, facts))
    return filter(facts, query_plan)
```

### 3. Invalidation (epoch-based)

On consolidation commit (T-032 single-transaction):
```
def on_consolidation_commit(persona_id):
    epoch_store.increment(persona_id)
    # Stale entries are detected lazily on next read (epoch mismatch)
```

No explicit eviction needed; stale entries are discarded when next read compares epochs. T-033's WAL `seq` field is the natural epoch primitive.

### 4. Size analysis

Per T-030: p75 persona ≈ 10 MB total storage.
- 6 domains × 10 MB / 6 ≈ **1.67 MB per (persona, domain) entry**
- 1,000 personas × 6 domains × 1.67 MB = **~10 GB** all-domains-cached

Realistically, only hot domains are cached (Biography hit every query; Psychometrics occasionally; Style rarely). Let's assume 2-3 domains hot per persona:
- 1,000 personas × 2.5 domains × 1.67 MB = **~4.2 GB**

H-102's prediction: "~100 MB per 1000 personas at p75". This is too low — the actual number depends on fact density. For p50 persona (2.5 MB total):
- 1,000 × 2.5 × 0.42 MB (per domain) = **~1 GB** at p50, a few GB at p75.

H-102 likely meant "per-domain" not "per-persona": 100 MB / 1000 personas = 100 KB per persona → tiny cache, only summary/keys.

**Revised sizing:** 
- Full-fact cache at p75: 4-10 GB per 1000 personas (on shared cache server).
- Hot-fact-only cache (just top-50 facts per domain): ~100 MB per 1000 personas (matches H-102).
- Either is workable on modest hardware (8-32 GB RAM per cache node).

### 5. Hit-rate analysis

Read-heavy workload:
- Answer path: 1-6 retrieval calls per query (per T-025 function-call catalog: planner routes to 1-6 domain retrievers).
- Extraction: rarely writes (only on ingestion; ~100 msg/mo for typical user).
- Ratio reads:writes ≈ 500:1 to 5000:1 for active users.

Cache hit rate:
- After warm-up (10-20 queries): >95% hit rate on read-hot domains.
- First-5-queries warm-up: 0-50% hit.
- Aggregate hit rate at steady state: **~92-97%** for typical user — exceeds H-102's ≥90% threshold. ✓

Invalidation frequency (consolidation cadence ~50 msgs from H-099):
- Active user: 100 msg/mo / 50 msg = 2 invalidations/mo per persona.
- Between invalidations: ~20-100 queries per invalidation cycle → cache remains warm most of the time.

### 6. Consistency guarantees

Epoch-based invalidation is "monotonic read consistency":
- Reader always sees facts from a consistent epoch (no torn reads).
- Writer's commit becomes visible on next read via epoch bump.
- No global clock required (per-persona epochs suffice under T-016 no-cross-persona).

### 7. Composition with T-021 (in-memory hash map)

T-021 describes an in-memory hash-map overlay over T-019 durability. The LRU cache is conceptually the same layer with explicit epoch-based invalidation — a refinement of T-021, not a new component.
