# E-038 Evidence

**OUTCOME: INCONCLUSIVE**

**Experiment:** E-038 (artifact-construction) — Hypothesis H-038 (single parametric retrieval tool `retrieve(persona_id, domain: enum[6], query: {field, value, op})`).

**Pass criterion:** (a) single tool schema ≤400 tokens (leaving ≥700 for planner); (b) planner output validates as function-call payloads; (c) §3.3's "domain-specific retrieval tools" (plural) is re-readable as aggregate CategoryRAG subsystem rather than literal 6 tools.

## Drafted parametric function-call schema

```json
{
  "name": "retrieve",
  "description": "CategoryRAG query against one of six memory domains.",
  "parameters": {
    "type":"object","additionalProperties":false,
    "properties":{
      "persona_id":{"type":"string","format":"uuid"},
      "domain":{"type":"string","enum":["biography","experiences","preferences","social_circle","work","psychometrics"]},
      "query":{
        "type":"object","additionalProperties":false,
        "properties":{
          "field":{"type":"string"},
          "value":{},
          "op":{"type":"string","enum":["eq","range","in"],"default":"eq"}
        },
        "required":["field","value"]
      },
      "limit":{"type":"integer","default":20,"maximum":50}
    },
    "required":["persona_id","domain","query"]
  }
}
```

## Token-accounting

Bare parametric schema: ~355 bytes → **~95 tokens (cl100k_base)**, plus ~15 tokens scaffolding ≈ **110 tokens**.

**But:** the parametric tool as drafted loses all per-domain field-enum validation (the `query.field` is open-typed `string`). If we want the planner to be guided toward canonical fields, per-domain field enums must be carried elsewhere — either:
1. In the tool `description` as natural-language text listing canonical fields per domain (adds ~180 tokens → total ~290 tokens, within 400-token target), OR
2. Via a discriminated union `oneOf` in the schema (adds ~350 tokens because 6 closed field-enums must be expressed — total ~460 tokens, **overshoots 400 tokens**).

### Size comparison

| Variant | Tokens |
|---|---|
| Bare parametric (open `field:string`) | ~110 |
| Parametric + field enums in description | ~290 |
| Parametric + `oneOf` discriminated union per domain | ~460 |
| 6-tool catalog (E-037) with trimmed scaffolding | ~745 |

The bare parametric schema (110 tokens) is dramatically smaller than the 6-tool catalog (~745). The description-embedded-enum variant (290 tokens) is still under 400 but bleeds tool-use machine-readability: the model sees "string, constrained by prose in description," which OpenAI function-call structured decoding cannot enforce.

## Planner-output validation

Example planner output:
```json
{"name":"retrieve","arguments":{"persona_id":"<uuid>","domain":"biography","query":{"field":"institution","value":"ucl","op":"eq"}}}
```

Validates against the drafted schema. Slot for a 2-domain multi-call becomes two `retrieve(...)` invocations in sequence, not a list — matches OpenAI function-call conventions.

## Paper-forensic reading of §3.3 plural "tools"

Quoted: "a planner LLM selects which domains to query, and **domain-specific retrieval tools** perform field-level matching against the structured JSON memory store—a mechanism we term CategoryRAG".

This passage is genuinely ambiguous:

- **Reading A (supports H-038):** "domain-specific retrieval tools" is aggregate language describing the CategoryRAG subsystem's per-domain routing, not a commitment to 6 literal OpenAI-function-call schemas. Figure 1 draws CategoryRAG as a single box.
- **Reading B (supports H-037):** "tools" is plural and immediately adjacent to "domain-specific" — grammatically singular-tool-with-domain-parameter would more naturally be "a domain-specific retrieval tool". The plural form commits to multiple tools.

**Neither reading is forced by the text.** Both are admissible given the paper's sparse architectural prose.

## Consistency with Wave-1 theories

- **T-012** (decomposed typed fields): the parametric variant weakens enforcement of canonical field names at the tool layer — they move into domain-internal logic instead of being visible at planner-call time.
- **T-016** (closed schema): the bare parametric tool has open `field:string`, which leaks into the planner layer. The description-embedded-enum variant restores closure in prose but not in structured decoding.

## Verdict reasoning

H-038's claim has two prongs:
1. **Size prong:** a single parametric tool fits in ≤400 tokens. **PASS** for the bare variant (110 tokens) and the description-enum variant (~290 tokens). **FAIL** for the discriminated-union variant (~460 tokens).
2. **Paper-reading prong:** §3.3's "domain-specific retrieval tools" is re-readable as aggregate subsystem. **AMBIGUOUS** — both readings are grammatically defensible; the text does not force disambiguation.

The bare parametric tool fits the size target but **sacrifices the closed per-domain field enums** that T-001/T-012/T-016 jointly require. The description-embedded-enum variant preserves size but not machine-readable enforcement. The discriminated-union variant preserves enforcement but overshoots the 400-token target.

Under the stated pass criterion, size alone ≤400 tokens is satisfied. But the deeper architectural question (does paper commit to 6 literal tools?) cannot be resolved from the text.

**E-037 (6-tool) already PASSED and is directly supported by the grammatical reading of §3.3. H-038 is architecturally admissible as an alternative implementation with meaningful tradeoffs but not strictly better.**

**OUTCOME: INCONCLUSIVE.** The drafted schema fits the 400-token budget in its bare form (110 tokens), and planner outputs validate. However:
- The bare parametric form loses per-domain field closure (T-012/T-016 tension).
- The fully-closed discriminated-union form overshoots 400 tokens.
- §3.3's plural "tools" is not resolvable either way from the paper text — both H-037 and H-038 remain readable.

H-038 is a plausible architectural alternative to H-037 but the paper does not force a choice, and the size-vs-closure tradeoff makes the two designs non-comparable without a stronger commitment from the paper. Downgrading to INCONCLUSIVE rather than PASS because the key disambiguator (paper's "domain-specific retrieval tools" plural) grammatically leans toward H-037 even though H-038 cannot be outright refuted.
