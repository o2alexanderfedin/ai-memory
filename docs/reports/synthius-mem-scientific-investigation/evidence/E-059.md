## Drafted Artifacts

### 1. Two-pass pipeline pseudocode

```python
# ------- Pass 1: raw extraction (no relevance field) -------
def extract_raw(chunk: str, domain: str, focal_persona: str) -> List[FactItem]:
    return openai.chat.completions.parse(
        model="gpt-4.1-mini",
        response_format=DOMAIN_SCHEMAS[domain],
        messages=[{"role":"system","content":EXTRACTION_PROMPTS[domain]},
                  {"role":"user","content":chunk}],
    ).choices[0].message.parsed.facts

# ------- Pass 2: batched salience classifier -------
SALIENCE_SCHEMA = {
  "type":"object","additionalProperties":False,
  "properties":{
    "scores":{"type":"array","items":{
      "type":"object","additionalProperties":False,
      "properties":{
        "fact_id":{"type":"string"},
        "salience":{"type":"string","enum":["peripheral","salient"]}
      },
      "required":["fact_id","salience"]
    }}
  },
  "required":["scores"]
}

CLASSIFIER_PROMPT = """Classify each fact as 'salient' (persistent user-relevant
attribute) or 'peripheral' (situational / environmental / phatic).
Return one score per fact_id."""

def classify_batch(facts: List[FactItem]) -> List[FactItem]:
    payload = [{"fact_id":f.fact_id,"text":f.evidence_quote,"fields":f.fields}
               for f in facts]
    result = openai.chat.completions.parse(
        model="gpt-4.1-mini",
        response_format=SALIENCE_SCHEMA,
        messages=[{"role":"system","content":CLASSIFIER_PROMPT},
                  {"role":"user","content":json.dumps(payload)}]
    ).choices[0].message.parsed
    keep = {s.fact_id for s in result.scores if s.salience == "salient"}
    return [f for f in facts if f.fact_id in keep]

# ------- Combined pipeline -------
def extract_and_filter(chunk, domain, focal):
    raw = extract_raw(chunk, domain, focal)
    return classify_batch(raw) if raw else []
```

### 2. A/B-testable threshold knob

Because the classifier is a separate prompt, operators can swap the rubric without re-extracting:
```
CLASSIFIER_PROMPT_EXHAUSTIVE = """Only classify as 'peripheral' if the fact
has NO plausible future relevance. When in doubt, mark 'salient'."""
```
This separation is the architectural upside H-059 claims over H-058.

## Checks performed

**(a) Design isolates relevance for A/B testing without re-extracting:** The pipeline's stage boundary means the classifier can be swapped, re-scored, or re-tuned against the same raw extraction corpus. A 3-threshold A/B ({strict, default, lenient}) re-runs only Pass 2 — dollars saved vs. H-058 which must re-extract. ✓

**(b) App. A.1 budget accommodates second pass — arithmetic:**

Per-chunk Pass 1 (single domain): ~740 tok/msg × messages_in_chunk.

Per-chunk Pass 2 (batched): cl100k_base counts:
- Classifier system prompt: ~80 tokens.
- Per-fact input: fact_id (8 tok) + evidence_quote (~25 tok) + fields (~20 tok) ≈ ~50 tok/fact.
- Per-fact output: `{"fact_id":"...","salience":"salient"}` ≈ ~15 tok/fact.
- Amortized: at K≈5 facts/chunk, Pass 2 costs ~(80 + 5×50 + 5×15) = 80 + 325 = **405 tokens/chunk**.

Per-msg share at ~12 msgs/chunk: ~34 tok/msg of Pass-2 overhead. Adding to Pass-1's 740 tok/msg gives ~774 tok/msg — **still within the same order** as App. A.1's stated 740. Matches the "cheap batched classifier at ~50-100 tok/msg amortized" target (34 is cheaper than the upper bound). ✓ Tight-but-feasible.

**(c) §5.2 "configurable" language matches operationally:** Classifier rubric is a string constant. Changing it mid-deployment requires only a prompt update, no schema/extraction change. ✓

**(d) Architecturally distinct from H-058:** H-058 includes `relevance: number` on the extraction output FactItem; H-059's FactItem has NO relevance field — salience is computed externally. A downstream observer can tell them apart by schema introspection. ✓

## Architectural competition — H-058 vs H-059

Per the task spec's explicit framing ("architectural winner depends on token cost which your arithmetic should show"):

| Dimension | H-058 (in-extractor score) | H-059 (two-pass classifier) |
|---|---|---|
| Extraction-call overhead per fact | +8-15 tok/fact (relevance field in schema + LLM output) | 0 (relevance NOT in primary schema) |
| Separate-call overhead per chunk | 0 | ~405 tok/chunk (system + I/O) |
| Per-msg amortized, K=5 facts, 12 msgs/chunk | +40-75 tok/msg (extract) | +34 tok/msg (classify) |
| Per-msg amortized, K=10 facts | +80-150 tok/msg | +68 tok/msg |
| Re-threshold cost | Re-extract entire corpus | Re-run Pass 2 only |
| A/B isolation | NO | YES |

**Verdict:** At low fact density (K≤5) H-058 is cheaper; at high fact density (K≥10) H-059 is cheaper AND offers free A/B isolation. Neither dominates; the architectural choice depends on the realized fact-density distribution. Both are buildable, both are PASS on internal consistency, and the token arithmetic favors H-059 at LoCoMo-realistic densities.

## Reasoning

- Two-pass pipeline drafted with explicit schemas for both stages.
- Arithmetic shows Pass-2 overhead is ~34 tok/msg amortized at K=5 facts/chunk (fitting App. A.1's 740 tok/msg budget within ~5% slack).
- A/B-test isolation is a genuine architectural advantage over H-058.
- §5.2 "configurable" language is operationalized via a swappable classifier prompt.
- Higher fact-density chunks (K≥10) push the combined budget ~9% above the stated 740 tok/msg — a warning but within "amortized average" rounding.
- Both H-058 and H-059 are architecturally defensible under internal-consistency checks; the downstream winner is a product/cost decision, not a paper-derivable one.
