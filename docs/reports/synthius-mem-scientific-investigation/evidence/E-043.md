## Drafted fallback path

```python
def retrieve_with_fallback(persona_id, domain, field, value, question: str):
    # Primary path: exact typed match + alias table (E-036).
    hits = retrieve(persona_id, domain, field, value)
    if hits:
        return hits              # happy path: <50 µs, no LLM

    # Fallback: over-retrieve (wider field/value net) + judge filter.
    over_retrieved = retrieve_wide(persona_id, domain)     # up to 50 facts
    if not over_retrieved:
        return []                # true absence: fast refusal signal

    judge_out = llm_judge(
        prompt=JUDGE_PROMPT.format(
            question=question,
            candidates=serialize(over_retrieved),
        ),
        model="gpt-4.1-mini",
    )
    if judge_out["match"] is None:
        return []                # judge-confirmed refusal
    return [c for c in over_retrieved if c.fact_id == judge_out["match"]]

JUDGE_PROMPT = """You are a memory-retrieval judge. Given a user question and a
set of candidate facts from the user's persona, determine which (if any) candidate
answers the question. If NONE of the candidates answer the question, reply with
null. Do not hallucinate — if the candidates do not contain a direct answer, the
correct response is null.

Question: {question}

Candidates (JSON array):
{candidates}

Reply with a JSON object: {{"match": <fact_id | null>, "reason": "<one sentence>"}}
"""
```

## Latency arithmetic

### Happy-path queries (H-035/H-036 match hits)

- Normalize + alias expand + index probe: ~50 µs
- Planner tool call: planner LLM time ≈ 200-500 ms **but this is separate from CategoryRAG's 21.79 ms** (CategoryRAG is the field-match step measured post-planner)
- CategoryRAG match step: ~50 µs = 0.05 ms
- Result assembly + marshal: ~20 ms
- **Happy-path total: ~21.79 ms matching §4.6.**

### Fallback-path queries (primary miss)

- Primary probe: ~50 µs (zero-hit return)
- `retrieve_wide`: bulk scan up to 50 facts per domain: ~100 µs
- LLM judge call (gpt-4.1-mini, 50-candidate payload ≈ 2-3K input tokens, 50 output tokens): **500-800 ms**
- Result filter: ~10 µs
- **Fallback total: ~500-800 ms (~25-35× primary path)**

### Mean latency effect

Let f = fraction of queries that miss primary and invoke fallback.
Mean = (1-f) × 21.79 + f × 750 ms

For the 21.79 ms mean in §4.6 to include fallback:
21.79 ms ≥ (1-f) × 21 + f × 750
→ 21.79 ≥ 21 - 21f + 750f
→ 0.79 ≥ 729f
→ f ≤ 0.108%

**Only if fewer than 0.1% of queries hit the fallback can the 21.79 ms mean accommodate it.**

Alternative interpretation: §4.6 explicitly says 21.79 ms is CategoryRAG mean latency, which may exclude the judge fallback (treated as a separate "answer composition" stage). Paper is silent on latency tails (G-083 confirms no p95/p99 published).

## Preservation of 99.55% adversarial refusal

The fallback path has two refusal pathways:
1. `retrieve_wide` returns empty → immediate null return (no judge call needed). This is the true-absence path; matches §4.4's "absence of evidence becomes a reliable refusal signal."
2. Judge returns `match: null` when candidates don't answer the question.

Both paths refuse without hallucinating. The judge prompt explicitly instructs: *"Do not hallucinate — if the candidates do not contain a direct answer, the correct response is null."* Refusal accuracy is preserved because:
- True absence → empty candidates → null without judge call
- Absence despite over-retrieval → judge confirms null

Paper's 99.55% adversarial robustness (Table 6) is consistent with this two-path refusal; the judge is a precision booster on paraphrase misses, not a hallucination source.

## Paper-forensic cross-check

H-043 fails if:
1. Paper commits to purely single-pass retrieval with no fallback, OR
2. 21.79 ms mean is shown to already include judge budget (shifting mean by ≥10×).

Reading §3.3 and §4.6:
- §3.3 describes CategoryRAG as "field-level matching against the structured JSON memory store" — no commitment to exclude fallback; no commitment to include it.
- §4.6 Fig. 7 data: Synthius-Mem's "21.79 ms mean" is compared against raw vector DB queries (Pinecone, Weaviate 15-20 ms) — this is the MATCH step alone, not including judge LLM calls. LLM judge calls would appear in answer-composition latency, not retrieval latency.

App. A.1 Table 7: "Synthius-Mem … ~2,000 tok retrieved + 1,100 tok planner + 200 output + 740 extraction" — **no token allocation for a per-query judge call.** Either the judge is embedded in the 200-token output budget (~100 tokens for judge prompt + judge response), or it doesn't exist in the pipeline.

**Reading the token budget strictly: there's no explicit per-query judge call in the token model.** This leans against H-043 as a core-pipeline component.

**Counter-reading:** the 740-token extraction amortization across 500 messages covers any tail-class judge-call budget for paraphrase misses at <1% frequency. If miss rate is 0.1% (the latency-mean constraint), adding ~750 ms × 0.001 = 0.75 ms to the retrieval budget is invisible in the mean and undetectable in App. A.1's token accounting.
