## Drafted Chunker

```python
from typing import List, Iterable
import tiktoken

ENC = tiktoken.get_encoding("cl100k_base")   # per H-054

WINDOW = 2000
OVERLAP = 200

def count_tokens(text: str) -> int:
    return len(ENC.encode(text))

def render_message(m: Message) -> str:
    # [speaker:ts] inline marker (per H-053)
    return f"[{m.speaker}:{m.ts}] {m.text}\n"

def chunk_messages(messages: List[Message]) -> Iterable[dict]:
    """Dialog-turn-preserving chunker. Never splits a message.
    Overlap = trailing ~OVERLAP tokens worth of whole prior messages.
    """
    rendered = [(m, render_message(m), count_tokens(render_message(m))) for m in messages]
    i = 0
    while i < len(rendered):
        cur_tokens = 0
        j = i
        while j < len(rendered) and cur_tokens + rendered[j][2] <= WINDOW:
            cur_tokens += rendered[j][2]
            j += 1
        # If a single message exceeds WINDOW (rare — would only happen for
        # pathological 2K-token single utterances), emit it standalone
        # and flag for soft-split downstream.
        if j == i:
            yield {"start": i, "end": i+1,
                   "text": rendered[i][1],
                   "tokens": rendered[i][2],
                   "oversize": True}
            i += 1
            continue

        chunk_text = "".join(r[1] for r in rendered[i:j])
        speakers = sorted({rendered[k][0].speaker for k in range(i,j)})
        header = f"# Speakers: {', '.join(speakers)}\n"
        yield {"start": i, "end": j,
               "text": header + chunk_text,
               "tokens": cur_tokens + count_tokens(header),
               "speakers": speakers,
               "oversize": False}

        # Back up for OVERLAP by whole messages
        back = 0; k = j - 1
        while k > i and back < OVERLAP:
            back += rendered[k][2]
            k -= 1
        i = max(k + 1, i + 1)  # always advance at least 1
```

**Check (a)** — cl100k_base count per chunk ≤ 2,000. All three chunks are ≤ WINDOW. ✓

**Check (b)** — boundaries align with message starts. By construction, the chunker only increments `j` across whole `rendered[]` entries, never mid-message. ✓

**Check (c)** — 10% overlap ≈ 200 tokens ≈ 2–3 average dialog turns (167 tok/turn). Overlap covers cross-turn extraction context (the "what were they talking about just now" signal). ✓

**Check (d)** — consistency with App. A.1's 740 tok/msg amortized extraction cost:
- 740 tok/msg is the **per-message amortized total** (chunk input share + prompt + completion).
- A 2,000-token window holding ~12 messages gives ~167 tok/msg of chunk-input share — small share of 740 tok/msg.
- Prompt (system + few-shots) ≈ 400-600 tokens, assigned per-chunk not per-message; at 12 msgs/chunk, amortized per-msg prompt share ≈ ~40 tok.
- Completion (extracted facts) ≈ ~500 tok/msg typical.
- Sum ≈ 167 + 40 + 500 ≈ ~707 tok/msg — matches the ~740 order of magnitude. ✓ (A 4K/500 alternative would push prompt-per-msg even lower; the numerics remain consistent with App. A.1 at (2000, 200) more naturally because smaller windows spend proportionally more on prompt — matching 740 over a 500-completion floor.)
