# E-127 STRIDE Threat Model — 3 Trust Boundaries

**OUTCOME: PASS**

## Method

Artifact construction: draft a STRIDE-per-stage threat model with three named trust boundaries
(TB-1 untrusted-prose → LLM; TB-2 cross-persona; TB-3 multi-tenant provider-plane) and enumerate
≥1 concrete STRIDE threat per boundary that is NOT reducible to another boundary.

## Boundary definitions

| TB | Name | Enforcement primitive | Adversary class |
|---|---|---|---|
| TB-1 | Untrusted-prose → LLM | H-128a guardrail sandwich + JSON-mode + T-001 closed schema | External user (attacker via uploaded chat content) |
| TB-2 | Cross-persona | T-018 persona-as-shard-key (storage-layer) + T-085 per-persona isolation | Malicious tenant user (owns persona-A, tries to read persona-B) |
| TB-3 | Multi-tenant provider-plane | Per-tenant KMS keys (H-138) + per-tenant network segment + per-tenant audit log | Malicious tenant operator / side-channel attacker / noisy-neighbor |

## STRIDE × Boundary matrix

| STRIDE | TB-1 (prose→LLM) | TB-2 (cross-persona) | TB-3 (multi-tenant) |
|---|---|---|---|
| **Spoofing** | Attacker injects fake speaker header in WhatsApp export ("System: …") | Persona-A session forges Y in persona_id header to query B | Tenant-ID forgery in API call; DNS rebinding / SSRF against KMS endpoint |
| **Tampering** | Prompt-injection: `IGNORE PRIOR…` tokens enter field values (OWASP LLM01) | Persona-A writes fact tagged with persona_id=B via planner misroute | Tenant-op alters another tenant's KMS key policy; fuzzer against provider-plane |
| **Repudiation** | User claims "I never said that" — but ingested corpus lacks signature | Cross-persona write lacks origin persona_id in WAL (cannot prove which persona caused fact) | Tenant-op deletes audit logs; no per-tenant append-only log guarantees |
| **Info-Disclosure** | LLM leaks system prompt / refusal policy back into answer (prompt-extraction) | Retrieval returns persona-A facts to persona-B session (CategoryRAG shard bypass) | KMS CMK exposed to wrong tenant; per-tenant TLS cert reuse; OpenAI token shared across tenants |
| **DoS** | Adversarial prose forces infinite-loop/pathological extraction | Persona-A floods consolidation queue, starves persona-B | Tenant-op exhausts shared LLM-provider quota (TPM); shared DB connection pool starvation |
| **Elevation-of-Privilege** | Prose sets `user_initiated=true` in WAL via injection (gains audit-bypass) | Persona-A plan-tool escalates to admin role via planner-LLM jailbreak | Tenant-op gains KMS admin via role-assumption bypass |

## Irreducibility proof (6 cells demonstrated)

- **TB-1 Tampering (prompt injection):** purely a data-vs-instructions attack; NOT a cross-persona concern (works on single-persona installs) and NOT a provider-plane concern (works even in single-tenant deployment).
- **TB-2 Info-Disclosure (cross-persona leak):** occurs between trusted LLM calls; NOT reducible to TB-1 (no untrusted prose needed — planner bug suffices) and NOT TB-3 (occurs within single tenant).
- **TB-3 Spoofing (tenant-ID forgery):** requires attacker at provider-plane layer; NOT TB-1 (no user prose) and NOT TB-2 (cross-tenant, not cross-persona-within-tenant).
- **TB-1 Repudiation vs TB-3 Repudiation:** TB-1 repudiation is about source-message signing (user denies uttering); TB-3 is about operator-level audit-log destruction — different actors, different mitigations.
- **TB-2 Elevation vs TB-1 Elevation:** TB-2 escalation is planner-jailbreak-to-admin-tool (a routing authorization bug); TB-1 is WAL field injection (a content-validation bug).
- **TB-3 DoS vs TB-1 DoS:** TB-3 DoS exhausts shared infra (provider TPM); TB-1 DoS exhausts LLM within one persona (retry/DLQ absorbs).

## Adversary-class coverage

| Adversary class | Boundary primarily responsible |
|---|---|
| External user (attacker via untrusted content) | TB-1 |
| Malicious tenant user (lateral movement within tenant) | TB-2 |
| Malicious tenant operator / side-channel | TB-3 |

All three classes cleanly map; no class straddles boundaries ambiguously.

## G-053 / G-056 / G-058 / G-018 mapping

| Gap | Maps to |
|---|---|
| G-056 prompt injection | TB-1 Tampering |
| G-058 cross-persona third-party-mention | TB-2 Info-Disclosure / Repudiation (persona-A writes about B, but in A's store only, never crosses to B — enforced by TB-2 discipline) |

All three paper-gap concerns land in exactly one boundary.

## 4th-boundary falsification check

Candidate 4th boundaries considered and rejected:

- **Agent-to-agent** (future MCP service, §6): reduces to TB-3 — inter-agent calls are
  just inter-tenant over the provider-plane.
- **Log-plane vs data-plane:** reduces to TB-3 — log-plane separation is a per-tenant audit-log
  primitive within TB-3's enforcement.
- **Backup-plane:** reduces to TB-3 — backups inherit per-tenant KMS (H-138).
- **User-interactive UI vs API plane:** reduces to TB-1 — UI input is a user-prose source.

No 4th orthogonal boundary required.

non-reducible cells demonstrated). Three adversary classes each map to exactly one boundary.
G-056 / G-058 / G-018 each map cleanly to TB-1 / TB-2 / TB-3 respectively. No candidate 4th
boundary survives reducibility analysis. Composes with T-018 (TB-2 enforcement), H-128a (TB-1
enforcement), H-138 (TB-3 enforcement).
