## Decision tree

```
on_extract(speaker=A, mentions=Bob, content=...):
    # Policy gate: NEVER write to B.store directly
    # Option 1 — DENY (drop):             data lost
    # Option 2 — ATTRIBUTE-AS-CLAIM:      stored in A.social_circle as A's claim about Bob
    # Option 3 — ATTRIBUTE-AS-FACT:       stored in both A.social_circle AND B.store (forbidden)
    #
    # SELECTED: Option 2 (ATTRIBUTE-AS-CLAIM to owner A)
    # Default-deny migration: B.store is NEVER auto-populated from A's mention
    ...
```

## Pseudocode

```python
def on_extract(
    speaker_persona_id: PersonaID,
    mentions: list[PersonRef],  # from T-010 dual-field {_raw, _ref}
    content: Fact,
    context_snippet: str,
):
    """
    When persona A's text mentions Bob (via name), we store the fact in A's Social Circle
    as A's claim about Bob. We NEVER write to Bob's persona store absent explicit consent.
    """
    for mention in mentions:
        bob_person_id = mention._ref  # resolved by T-015 Social-Circle alias; may be None

        # Step 1: write to A.social_circle with claim metadata
        claim = {
            "person_id": bob_person_id or generate_new_person_id(),
            "names": [mention._raw],
            "claims": [{
                "content": content,
                "claim_source": speaker_persona_id,     # A is the source
                "claim_type": "hearsay",                 # A reported, not B
                "confidence": extraction_confidence,
                "evidence_quote": context_snippet,
                "extracted_at": now_utc(),
            }],
        }
        upsert_social_circle_claim(speaker_persona_id, claim)

        # Step 2: default-deny migration
        # DO NOT write to B.store under any circumstances here.
        # If Bob is a tenant and consent is configured, emit a consent request.
        if bob_person_id and is_tenant_persona(bob_person_id):
            # IMPORTANT: this uses an allow-list of pre-approved B tenants only.
            # In a multi-tenant deployment, cross-tenant consent requests are
            # typically DISABLED at service layer (opt-in per deployment).
            if cross_tenant_consent_enabled(speaker_persona_id, bob_person_id):
                enqueue_consent_request(
                    from_persona=speaker_persona_id,
                    to_persona=bob_person_id,
                    facts=[content],
                    consent_ttl=30 * 24 * 3600,  # 30 days
                )


def on_consent_granted(consent_token: ConsentToken):
    """
    Called when Bob clicks 'Accept' in the consent UI.
    Only then do facts flow into B's store.
    """
    assert consent_token.verify_signature()       # tamper-evident
    assert consent_token.to_persona == current_persona_id()
    assert consent_token.granted_at is not None
    # Copy facts into B.store with provenance referencing A's claim
    for fact in consent_token.facts:
        b_fact = {
            **fact,
            "provenance": {
                **fact.provenance,
                "source_persona_id": consent_token.from_persona,  # A
                "consent_token_id": consent_token.id,
                "consent_granted_at": consent_token.granted_at,
            },
        }
        upsert_b_store(consent_token.to_persona, b_fact)
```

## Enforcement at storage layer (T-018)

Under T-018 persona-as-shard-key:
- Writes are routed by `persona_id` to the correct shard.
- `upsert_b_store(persona_id=B, ...)` requires the write path to carry a consent-token as
  metadata. The storage-layer guard rejects any write to persona-B's shard that does NOT
  originate from B's own session OR from a valid consent-token flow.

```python
def storage_write_guard(writing_session_persona, target_persona, metadata):
    if writing_session_persona == target_persona:
        return True  # self-write allowed
    if metadata.get("consent_token_id") and verify_consent_token(metadata.consent_token_id):
        return True  # cross-persona write via consent
    return False  # REJECT
```

**No write path exists from A-extraction into B-store absent consent-token.** Structural
enforcement.

## GDPR lawful-basis mapping

| GDPR Article | Application |
|---|---|
| Art. 6(1)(a) Consent | B provides explicit consent via consent-token UI before A's claims migrate |
| Art. 6(1)(f) Legitimate interest | NOT used here — cannot justify cross-persona auto-write of B's data without B's knowledge |
| Art. 14 Notice to data subject | When Bob is a tenant, consent request acts as the Art. 14 notice: "Alice mentioned you; here are the facts she reported. Do you want to import them?" |
| Art. 15 Right of access (when Bob is a tenant) | Bob's persona inspect endpoint shows only B-owned facts; facts A reported about Bob are NOT in B's store |
| Art. 17 Erasure | Bob can erase his persona; does NOT erase A's claims about Bob in A.social_circle (those are A's data, Art. 17 scope is per-subject) |

## Synthetic fixture

**Setup:**
- Alice uploads WhatsApp export mentioning Bob 5 times (e.g., "Bob and I went to Paris in
  June 2023").
- Alice's Biography/Experiences extractors process.
- Bob is a Synthius-Mem tenant on the same deployment.

**Expected outcome:**
- Alice's `social_circle[Bob]` contains 5 claim records: `{claim_source: Alice,
  claim_type: hearsay, confidence: 0.7, evidence_quote: "<verbatim>"}`.
- Alice's `experiences[Paris 2023]` contains `social_context: [{_raw: "Bob", _ref: "B's
  person_id"}]` (T-010 dual-field).
- **Bob's store is UNCHANGED.** No writes to Bob's biography, experiences, social_circle,
  preferences, work, or psychometrics.
- Bob receives ONE consent-request notification aggregating the 5 facts.
- If Bob accepts: the 5 facts are copied into Bob's store (probably as `experiences` in
  Bob's own timeline) with `provenance.source_persona_id=Alice, consent_token_id=<uuid>`.
- If Bob declines (or times out): no migration; A's claims persist in A's store only.

**Assertions:**
- `count(writes_to_bob_store) == 0` before consent.
- `count(consent_notifications(bob)) == 1` (aggregated).
- `count(writes_to_bob_store) == 5` after consent; all carry consent_token_id.
- `count(writes_to_bob_store_without_consent_token) == 0` across full fixture.

## Single-tenant collapse check

If Synthius-Mem runs single-tenant (e.g., on-premise per-user installs), then "Bob as tenant"
is undefined — Bob is just a Social-Circle person, never a tenant persona. In that case:
- `is_tenant_persona(bob_person_id) == False` always.
- No consent-request flow fires.
- Bob's facts live only in Alice's social_circle as claims.
- Cross-persona contamination risk collapses to zero (there's no B-store to contaminate).

**The hypothesis is NOT mooted** — the attribute-as-claim-to-owner pattern is still the
right default even in single-tenant, because it preserves claim-attribution semantics
(A reported X about Bob, not "X is a fact about Bob").
