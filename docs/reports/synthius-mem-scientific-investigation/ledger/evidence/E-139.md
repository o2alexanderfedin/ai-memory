**OUTCOME: PASS**

## Method

Artifact construction: extend T-009 shared provenance envelope with `injection_risk` (from
H-128b) and `pii_tokens_redacted` (from H-133); validate additive-only (no breaking changes),
WAL compatibility, DSAR exposure, and no field conflicts across all six domain schemas.

## Extended provenance envelope

```json
{
  "$defs": {
    "Provenance": {
      "type": "object",
      "additionalProperties": false,
      "required": ["source_message_id", "source_chunk_id", "extracted_at", "extractor_version"],
      "properties": {
        "source_message_id": { "type": "string", "format": "ulid" },
        "source_chunk_id":   { "type": "string", "format": "ulid" },
        "extracted_at":      { "type": "string", "format": "date-time" },
        "extractor_version": { "type": "string", "pattern": "^\\d+\\.\\d+\\.\\d+$" },

        // -------- H-139 additive extensions ----------
        "injection_risk": {
          "type": "number", "minimum": 0, "maximum": 1,
          "description": "From H-128b detection LLM. 0=benign, 1=high injection risk."
        },
        "pii_tokens_redacted": {
          "type": "array",
          "items": {
            "type": "object",
            "additionalProperties": false,
            "required": ["type", "original_token_hash", "replacement_tag"],
            "properties": {
              "type": {
                "type": "string",
                "enum": ["PHONE", "EMAIL", "SSN", "CREDIT_CARD", "PERSON",
                          "LOCATION", "DATE_TIME", "IP_ADDRESS", "URL",
                          "MEDICAL_LICENSE", "CRYPTO_WALLET", "PASSPORT",
                          "DRIVER_LICENSE", "NATIONAL_ID", "OTHER"]
              },
              "original_token_hash": {
                "type": "string", "pattern": "^[a-f0-9]{64}$",
                "description": "SHA-256 of original token + per-tenant salt"
              },
              "replacement_tag": { "type": "string" }
            }
          }
        }
      }
    }
  }
}
```

Both new fields are **optional** (absent from `required`). Absence means benign / no PII found
(the common case). Presence carries the security/privacy annotation.

## (a) Additive-only check

| T-009 original field | Status | Notes |
|---|---|---|
| `source_message_id` | UNCHANGED | Still required |
| `source_chunk_id`   | UNCHANGED | Still required |
| `extracted_at`      | UNCHANGED | Still required |
| `extractor_version` | UNCHANGED | Still required |
| `injection_risk`    | **NEW (optional)** | Added; old T-009 consumers that don't read it are unaffected |
| `pii_tokens_redacted` | **NEW (optional)** | Same |

JSON Schema Draft 2020-12 additive extension pattern: adding optional fields is a
non-breaking change under the `$defs.CommonEnvelope` + `$ref` composition (T-003). Old
consumers reading `provenance.source_message_id` see the same value; new consumers reading
`provenance.injection_risk` get the annotation or `undefined`.

No breaking change to T-009 consumers. ✓

## (b) WAL composition (T-033)

T-033 WAL record schema: `{persona_id, seq, op, domain, fact_id, delta{before, after},
timestamp, extractor_version, user_initiated: bool}`.

Proposed extension: WAL records whose `delta` includes an envelope with extended provenance
carry the same `injection_risk` and `pii_tokens_redacted` within the envelope. Add one
OPTIONAL top-level WAL field:

```json
{
  // ... existing T-033 fields ...
  "provenance_audit": {
    "type": "object",
    "injection_risk_at_extract": 0.02,
    "pii_redacted_count": 3,
    "pii_redaction_versions": ["presidio-2.2.1"]
  }
}
```

(Redundant with in-envelope values, but provides WAL-level summary without decrypting
the full delta payload — useful for retention policy decisions.)

WAL replay (E-132 primitive b) sees the extended fields as metadata; idempotency via
record-ID dedup is unchanged. ✓

## (c) DSAR exposure (H-136 Art. 15)

The `/persona/{id}/export` endpoint (H-136) returns the full `provenance_chain` array per
fact. With the H-139 extension:

```json
{
  "fact_id": "...",
  "domain": "biography",
  "category": "residence",
  "fields": {"city": "[LOCATION]", "country": "DE"},
  "provenance": {
    "source_message_id": "01HX...",
    "source_chunk_id": "01HX...",
    "extracted_at": "2026-01-15T12:34:56Z",
    "extractor_version": "2.1.0",
    "injection_risk": 0.01,
    "pii_tokens_redacted": [
      {"type": "LOCATION", "original_token_hash": "abc123...", "replacement_tag": "[LOCATION]"}

```

User can SEE:
- That extraction considered the message (timestamp + extractor version).
- That PII was redacted pre-LLM (type + replacement tag; actual original token hidden under
  hash, but redaction fact disclosed).
- That injection risk was assessed (score visible).

**Satisfies Art. 15 right-of-access including the "logic involved in automated processing"
per Art. 15(1)(h) + EU AI Act Annex III inspection right.**

## (e) GDPR-erasure cascade check

T-009 established the cascade: erasure of `source_message_id=M` → cascade-delete all facts
whose `provenance.source_message_id == M`.

With H-139 extension:
- `pii_tokens_redacted.original_token_hash` is a deterministic hash with per-tenant salt;
  erasing the tenant → destroying the salt → hashes become unrecoverable. ✓
- `injection_risk` is a scalar annotation, fully erased by the cascade. ✓
- No new cascade path introduced; `source_message_id` remains the single erasure key.

Composes cleanly with H-137 crypto-shredding and H-140 tombstone-purge. ✓
