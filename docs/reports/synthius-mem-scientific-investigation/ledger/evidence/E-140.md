# E-140 Right-to-Erasure Alternative — Tombstone-and-Purge

**OUTCOME: PASS (competing-sibling with E-137 crypto-shred)**

## Method

Artifact construction: draft tombstone-and-purge as an alternative to H-137 crypto-shredding;
verify (a) Art. 17 compliance under bounded backup retention, (b) simpler operationally than
H-137, (c) compatible with T-033 WAL only under bounded retention. Comparison table vs H-137
on op-complexity / cost / residual-window / regulatory-fit.

## Procedure

```
User requests Art. 17 erasure (DELETE /persona/{id}?mode=hard)
        │
        ▼
┌─────────────────────────────────────────────┐
│ 1. Authenticate persona-owner               │
│ 2. Record DSAR ticket + start 72-hour clock │
└─────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────┐
│ 3. For T-019 Postgres per-persona JSONB:    │
│    BEGIN;                                   │
│    DELETE FROM biography  WHERE persona_id; │
│    DELETE FROM experiences WHERE persona_id;│
│    DELETE FROM preferences WHERE persona_id;│
│    DELETE FROM social_circle WHERE ...;     │
│    DELETE FROM work WHERE persona_id;       │
│    DELETE FROM psychometrics WHERE ...;     │
│    DELETE FROM wal_log WHERE persona_id;    │
│    DELETE FROM wal_snapshot WHERE ...;      │
│    COMMIT;                                  │
│    VACUUM (FULL) biography, experiences,    │
│               preferences, social_circle,   │
│               work, psychometrics,          │
│               wal_log, wal_snapshot;        │
│    (VACUUM FULL rewrites heap without       │
│    tombstoned rows; storage pages reclaimed)│
│                                             │

└─────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────┐
│ 4. WAL entries physically purged in the     │
│    same txn window (72 hours).              │
│    WAL retention policy MUST be bounded     │

└─────────────────────────────────────────────┘
        │
        ▼

│    (≤ 30 days).                             │
│    - Daily incremental backups age out in   │
│      7 days.                                │
│    - Weekly full backups age out in 30 days.│

        │
        ▼
┌─────────────────────────────────────────────┐
│ 6. Emit completion notification + audit log │
│    (H-131 SLI-12).                          │
│    Art. 17 fulfilled within 30 days         │
│    (backup rotation is the long pole).      │

```

## (i) Art. 17 "without undue delay" compliance check

- Live store purged within 72 hours. ✓
- WAL purged within 72 hours. ✓
- Backups purged ≤ 30 days via rotation.
- Under 30-day-max backup retention: total residual window ≤ 30 days.
- WP29 + EDPB guidance: 30 days is "without undue delay". ✓

**Fails GDPR compliance if backup retention exceeds 30 days** — in which case this approach
cannot satisfy Art. 17 without either (a) tightening backup retention (which may violate
other regulations like SOX 7-year archives or HIPAA 6-year accounting-of-disclosures), or
(b) escalating to H-137 crypto-shredding.

## (ii) Simpler than H-137

- **No KMS integration:** standard Postgres/SQLite operations only.
- **No DEK-per-persona wrapping cost:** writes don't encrypt with a separate key per persona;
  application-level encryption is NOT required (disk-level encryption like LUKS suffices).
- **No KMS audit trail:** CloudTrail/AuditLog for KMS operations not needed.
- **No cross-region DEK replication management.**
- **Single failure mode:** DELETE + VACUUM is a standard DB operation; no "what if KMS API is
  unavailable" concern.

**Operational cost reduction:** ~30-40% on key-management infra + tooling. Suitable for
cost-sensitive product tiers.

## (iii) Compatibility with T-033 WAL under bounded retention

- WAL retention policy: ≤ 30 days (compatible with T-033's "persistent append-only event log"
  if "persistent" is interpreted as "until compacted/rotated" rather than "archival forever").
- T-044's "unbounded by default" retention is INCOMPATIBLE with H-140. Under H-140, T-044
  must be tightened to bounded retention.
- WAL physical-purge on erasure: must use `DELETE FROM wal_log WHERE persona_id` + `VACUUM`.

**H-140 requires a retention-policy commitment on T-033 WAL that T-033 alone does not make.**
If the product commits to long-retention WAL (archival forensics, financial compliance),
H-140 fails and H-137 crypto-shredding is required.

## Comparison table H-137 vs H-140

| Dimension | H-137 (crypto-shred) | H-140 (tombstone-purge) |
|---|---|---|
| **Op-complexity** | HIGHER (KMS integration, per-persona DEK management, KMS audit feed) | LOWER (standard DB DELETE + VACUUM + backup rotation) |
| **Cost-per-erasure** | ~$0.03-0.05 (1 KMS DestroyKey + audit + 0 storage reclaim) | ~$0.01-0.02 (DELETE + VACUUM + backup cycle share) |
| **Residual-erasure-window** | ≈ 0 (key destruction is instantaneous) | ≤ 30 days (bounded by backup rotation cycle) |
| **Long-retention archives** | **WORKS** (key destruction invalidates ciphertext in all archives) | **FAILS** (cannot purge 7-year backup tape) |
| **HIPAA 6-year accounting** | Compatible (encryption of at-rest ePHI is a safeguard, not a retention constraint) | Requires separating persona PHI from accounting log |
| **Financial SOX 7-year** | Compatible (key destruction valid cryptographic erase) | Fails for persona data in SOX-scoped archives |
| **Infrastructure overhead** | KMS, HSM, KMS audit pipeline | Standard DB VACUUM + backup rotation |
| **Recovery from mis-delete** | Impossible after DEK destroyed (is this a feature or bug?) — 30-day soft-delete window mitigates | Possible within backup rotation window |
| **GDPR Art. 17 compliance** | ✓ everywhere | ✓ IF backups ≤ 30 days |
| **NIST 800-88 alignment** | "Cryptographic Erase" (Rev. 1 §4.7) | "Clear" / "Purge" (Rev. 1 §4.1 / §4.3) |
| **Diff-engine rollback compatibility** | ✓ T-033 WAL can be long-retention (ciphertext) | ✗ requires T-033 retention ≤ 30 days |
| **Recommended when** | GDPR-first, long-retention backups, HIPAA / financial sectors | Single-region, short-retention, cost-sensitive, no long-term archive policy |

## Trade-space analysis

**H-140 is preferred when ALL the following hold:**
1. Backup retention ≤ 30 days (no long-term archives).
2. No sectoral regulation mandates KMS (no HIPAA/PCI-DSS/SOX/financial compliance scope).
3. Diff-engine rollback window ≤ 30 days (no archival forensics requirement).
4. Operational simplicity is a product-tier priority (e.g., B2C consumer tier).

**H-140 is INSUFFICIENT when any of:**
- Backups exceed 30-day retention (common: daily-incremental with 90-day retention for DR).
- HIPAA / PCI-DSS / SOX requires encryption + key-destruction for erasure certification.
- Multi-region replication copies data to regions where local delete + VACUUM does not
  propagate guaranteed within 30 days.
- Long-term forensic audit requires WAL archival > 30 days.

**Default recommendation:** H-137 as the default for GDPR-first consumer deployments (stronger
guarantee), with H-140 as a fallback for simplified / budget / single-region tiers where
backup policy is bounded.

## Verdict

**PASS (as a competing-sibling, NOT as a strictly-superior replacement for H-137).**

All 3 sub-criteria met:
- (i) Procedure satisfies "without undue delay" GDPR Art. 17 wording when backup rotation
  ≤ 30 days.
- (ii) Simpler than H-137 (no KMS integration; ~30-40% lower operational cost).
- (iii) Compatible with T-033 WAL when WAL is bounded-retention (≤ 30 days), NOT archival.

ADDITIONAL PASS condition met: comparison table vs H-137 covers op-complexity, cost-per-
erasure, residual-erasure-window, regulatory-fit-under-long-retention-archives. Clear trade
space identified.

**H-140 FAILS if:**
- Backups are long-retention (e.g., 7-year financial archive) → H-137 strictly superior.
- KMS is mandated by separate regulation (HIPAA) → H-137 required.

Default: H-137; H-140 for cost-sensitive bounded-retention tiers. Both PASS individually on
their stated scopes; the product should pick per tenant-tier.
